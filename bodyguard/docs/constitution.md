# Bodyguard Constitution

> 이 문서는 **기능 목록이 아니다.** 설계 판단이 갈릴 때 꺼내 보는 기준이다.
> 지시가 없는 상황에서 무엇을 고를지 알려주는 것이 이 문서의 역할이다.

최종 갱신: 2026-09-26 · 근거: `research/01` 원문, 과목 차터

원칙마다 근거를 적었다. `[PO 제안]`은 사용자에게 확인받지 않은 원칙이다(`open-questions.md` Q-25).

## 제품 원칙

### P1. 영상은 브라우저를 떠나지 않는다
카메라를 켜는 서비스다. 사용자가 믿고 켜 둘 수 있어야 한다.
- 영상 프레임은 추론에만 쓰고 바로 버린다. 녹화·캡처·전송은 어떤 이유로도 하지 않는다
- 관절 좌표도 지표로 바꾼 뒤 버린다. 서버에는 1분 요약만 간다
- "나중에 계산식을 바꿀 때 필요할 것 같다"는 좌표를 저장할 이유가 되지 않는다
- 리포트 요약을 만들 때 외부 LLM에는 집계 숫자만 보낸다. 이름·이메일은 보내지 않는다

근거: 원문 8, 34, 41

### P2. 진단하지 않는다. 측정값으로만 말한다
- "거북목이 의심됩니다" 대신 "목 이탈 비율이 평소보다 높았다"
- 원인·질환·치료를 말하지 않는다. 판단은 의료진의 몫이다
- 리포트는 진단서가 아니라 측정 기록이다

근거: 원문 5, 8

### P3. 애매하면 판정하지 않는다 `[PO 제안]`
틀린 빨간색은 신뢰를 깎고, 틀린 "통과"는 스트레칭을 무의미하게 만든다. 아무 말 안 하는 것보다 틀린 말이 더 나쁘다.
- 관절이 잘 안 보이면 추정해서 채우지 않고 "측정 불가"로 둔다
- MediaPipe는 가려진 관절도 좌표를 지어낸다. 가시성으로 거른다
- 판정률을 올리려고 불확실한 값을 쓰지 않는다
- 제품 아바타에는 확인 불가 부위를 별도 색으로 칠하지 않는다. 필요한 촬영 위치만 안내하고 내부 성공 판정은 멈춘다

### P4. 기준은 남이 아니라 나다
체형도, 노트북 위치도, 앉는 버릇도 사람마다 다르다. 모두에게 같은 각도를 들이대지 않는다.
- 정자세는 보정 때 찍은 내 자세다
- 절대 기준이 성립하는 건 어깨 기울기(수평)뿐이다
- 보정 자세가 나쁘면 판정도 틀어진다. 그래서 보정 화면이 가장 친절해야 한다

근거: 과목 PRD F-02

### P5. 켜 둔 동안만 재고, 켜져 있다는 걸 항상 보여준다
- 웹을 켜야 측정한다. 페이지를 닫으면 끝난다
- 측정 중에는 화면에 항상 표시한다 `[PO 제안]`
- 사용자가 모르는 사이에 카메라가 도는 순간이 있으면 안 된다

근거: 원문 30

### P6. 방해는 이유가 있을 때만
작업을 돕는 서비스가 작업을 끊으면 꺼진다.
- 알림은 자세가 5분 무너졌거나 50분 앉아 있었을 때만 띄운다
- 기준은 사용자가 바꾸고 끌 수 있다
- 같은 알림을 연달아 띄우지 않는다

근거: 원문 32

### P7. 하지 않은 스트레칭은 한 것으로 치지 않는다
- 건너뛰면 건너뜀으로 기록한다
- 판정할 수 없으면 통과시키지 않는다
- 기록을 좋게 보이려고 판정을 느슨하게 하지 않는다

근거: 과목 PRD 예외 5

### P8. 가볍게 돈다
카메라를 켜 두는 서비스라 무거우면 안 켠다.
- 필요한 만큼만 추론한다(보일 때 30fps, 가려지면 1초 간격)
- 움직이는 두 아바타는 실제 노트북에서 부드럽게 재생되는 범위로 최적화한다. 정지 시에는 불필요한 렌더링을 피한다
- 무게는 느낌이 아니라 숫자로 잰다(M-5)

근거: 원문 30

## 기술 원칙

### T1. 판정 로직은 카메라 없이 테스트한다
`posture/`와 `stretch/`는 브라우저 API에 의존하지 않는 순수 TypeScript다.
관절 좌표 픽스처를 넣어 Vitest로 검증한다. 임계값을 바꿀 때마다 수백 개 샘플을 몇 초 안에 돌린다.

### T2. 검증 전에는 확정하지 않는다
MediaPipe·Three.js·PyOD는 프로토타입으로 확인하기 전까지 "검증 대상"이다.
문서에도 코드 주석에도 확정 표현을 쓰지 않는다.

근거: 원문 19

### T3. 임계값은 한곳에 모은다
판정 수치는 전부 `posture/thresholds.ts` 같은 한 파일의 상수다. 실측하면서 계속 바뀐다.
코드 곳곳에 숫자를 흩어 두면 어떤 값이 판정을 바꿨는지 추적할 수 없다.

### T4. 측정할 수 없으면 목표가 아니다
15fps, 1초, 80%는 재는 장치가 있어야 목표다. 디버그 패널과 로그를 **초기에** 넣는다.

### T5. 잘 만들어진 것은 가져다 쓴다 `[PO 제안]`
포즈 추정, 3D 렌더링, PDF, 자연어 요약(LLM)은 검증된 도구를 활용한다. 출시용 남녀 3D 모델·리그·동작은 Blender로 제작한다. 판정, 기준선, 알림 규칙, 스트레칭 판정은 직접 만든다.
인증은 팀이 만들어 본 경험이 있어 직접 만든다(원문 42). 나머지 시간은 판정과 스켈레톤에 쓴다.

### T6. 한 커밋은 한 가지 일만 한다
AI 에이전트는 커밋을 크게 만드는 경향이 있다. 작게 유지한다.

## 충돌 시 우선순위 `[PO 제안]`

판단이 갈리고 위 원칙으로도 결론이 안 나면 **이 순서**로 정한다.

```
1. 개인정보     — 영상·몸 데이터가 새지 않는가
2. 오판정 방지   — 틀린 판정을 내지 않는가
3. 실시간성     — 1초 안에 반응하는가
4. 기능        — 할 수 있는 게 많은가
```

기능이 맨 아래다. **기능을 늘리려고 위의 셋을 내주지 않는다.**

자주 부딪히는 판단:
- 판정률과 오판정이 부딪히면 → **오판정을 막는 쪽**
- 애매한 자세는 → **측정 불가**
- 기록을 더 자세히 남기는 것과 개인정보가 부딪히면 → **개인정보**
