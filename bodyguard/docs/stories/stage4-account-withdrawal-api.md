## 범위와 의존성

4단계 계정·데이터 관리의 이미 승인된 탈퇴 기능을 구현한다. 기록 삭제 웹 S4.4의 검증이 진행 중이어도 서버 계정 탈퇴 계약·합성 HTTP/SQL 하네스는 독립적이므로 최신 main의 별도 `codex/stage4-account-withdrawal`에서 준비한다. S4.4와 목적을 섞어 병합하지 않는다.

S4.4는 PR #23, merge commit143090bb3dcfc2902b373deca6595cce8ddd5c10의 main 포함·브랜치 보존을 실제 확인했다. 현재 Story도 최신 main으로 갱신했다. CEO의 추가 확인대로 제품은 노트북 **브라우저 웹사이트**이며 설치형 앱·모바일/네이티브 앱을 만들지 않는다. 후속 탈퇴 화면도 기존 웹 내비게이션·계정 경계에 연결한다.

CEO 지정 web-design-studio를 통한 화이트·블루 공통 디자인은 PR #24/main7b95cfc에 병합됐다. 실제 가입→시작→탐색→기록과 삭제 흐름·좁은 창·키보드를 검증하고 실패도 보존했다. 이 API 작업은 디자인 변경과 섞지 않고 별도 Story로 이어가며, 후속 웹은 docs/web-design.md를 따른다. 이전 아바타 부위의 새 사이클은 시작하지 않았다.

운영·실제 사용자 삭제, 실제 Gmail/Google 연결, 개인정보 문서 확정·보관 정책(Q-17)·백업 보존 정책·배포는 제외한다. 현재 코드의 본인 요청 삭제와 사업·법무 정책 확정은 다르다. 계정 탈퇴 웹은 별도 Story이며 API 명세만으로 작동하는 버튼을 공개하지 않는다. 아바타/실측·실제 코칭은 기존 이월 게이트를 유지한다.

## CTO 권장 기술 계약

현재 로그인만으로 되돌릴 수 없는 계정 삭제를 허용하지 않는다. 이미 검증된 본인 이메일로 **탈퇴 전용 인증 코드**를 보내고 현재 세션에서 그 코드와 명시 확인문을 제출할 때만 삭제한다. 이메일/구글 계정 모두 검증된 이메일을 사용하며, 가입 코드·비밀번호 복구 토큰·다른 세션/계정의 코드는 재사용할 수 없다. 실제 공급자 연결은 승인 전까지 합성 메일로만 검증한다.

- 시작: 인증·Origin/CSRF 검사를 통과한 현재 계정만 요청 가능. 요청 body에 이메일·user_id를 받지 않는다. 메일 수신지를 현재 본인 계정에서 가져온다. 읽기·전송·코드 발급만으로 삭제하지 않는다.
- 확인: 고정 `delete-my-account` 확인문,43자 난수 challenge 식별자,6자리 코드를 검사한다. 코드와 challenge는 목적별 해시만 저장하고 응답·로그에 코드/쿠키/비밀번호를 넣지 않는다. 한 계정의 새 요청은 이전 확인을 폐기하며10분 만료·최대5회 오입력·요청 횟수 제한을 적용한다.
- 메일 전송 실패는 성공으로 표시하지 않는다. 실패한 확인값은 사용할 수 없게 폐기한다. 재시도는 사용자의 명시 요청이며 자동 삭제 재시도는 없다.
- 삭제: 현재 계정·인증 세션·credential version·미사용/미만료 challenge를 잠금 뒤 다시 검사한다. 계정과 현재 구현된 본인 수행 기록·세션·복구 확인·구글 흐름을 한 transaction에서 제거한다. 다른 계정·공유 IP의 보안 제한은 제거하지 않는다. 본인 이메일의 가입 잔여 확인과 이메일별 보안 제한도 정리한다.
- 응답: 실제 transaction 완료 후204 및 세션 쿠키 삭제. 삭제 전 권한/확인 실패 또는 DB 실패에서 본인/타인 자료를 부분 삭제하지 않는다. 중복/경쟁 확인이 추가 계정에 영향을 주지 않으며 이전 쿠키·복구/가입 확인으로 삭제된 계정의 데이터나 인증을 복구하지 못한다.

전용 확인 테이블은 새 migration으로 추가한다. 기존 migration을 수정하지 않는다. 아직 구현되지 않은 요약·설정·알림·리포트 테이블의 전부 삭제 연결과 운영 백업/복구 검증은 최종 통합·운영 게이트다. 현재 테이블만 제거하고 전체 서비스 데이터 관리가 완성됐다고 선언하지 않는다.

### 구현 전 잠금 검토

삭제는 여러 세션과 FK를 동시에 제거하므로 현재 요청 세션만 먼저 잠근 뒤 user 행을 잠그는 방식은 쓰지 않는다. 비밀번호 변경의 user→session 순서와 기록 저장의 session→FK key-share를 함께 고려한다. 탈퇴 시작/확인은 인증 세션을 잠금 없이 사전 조회한 다음 user의 `FOR NO KEY UPDATE`→현재 세션 재검증/잠금→전용 확인 순서로 직렬화하는 권장안이다. FK key-share와 충돌하는 DELETE는 기록 쓰기 transaction 완료를 기다리며 이후 실제 경쟁 하네스로 확인한다. 이 설계만으로 교착 없음 또는 경쟁 통과를 주장하지 않는다.

일반 transient cleanup에 전용 확인 테이블 삭제를 곧바로 넣지 않는다. 타인의 만료 세션을 잠근 cleanup과 탈퇴 cascade가 반대 순서로 기다릴 수 있으므로 경쟁 검증 전에는 사용하지 않는다. 확인 상태는 계정당 한 행으로 제한하고 새 요청/본인 탈퇴가 이전 상태를 대체·제거한다. 가입 잔여 확인 제거는 사용자 cascade 뒤 이메일별 quota를 잠그고 최신 snapshot에서 수행하는 순서까지 검증한다. 익명 공유 IP 제한은 다른 계정 보호를 위해 남긴다.

## 수용 하네스와 통과 기준

격리된 합성 PostgreSQL18·실제 FastAPI로 처음에는 미구현 red를 기록하고 다음을 검증한다.

1. 본인 시작→전용 코드→명시 확인→204, 실제 본인 계정/수행 기록·인증 세션 제거 및 타 계정 보존.
2. 미리보기/전송/취소·GET·잘못된 확인문·Origin/CSRF 누락·게스트에서 삭제0.
3. 가입 코드/복구 확인·타 계정/새 세션 코드·만료/오입력·재발급 전 확인값 거부.
4. 실제 전송 실패·DB transaction 실패에서 삭제0/정확한 실패, 요청 제한과 오입력 제한.
5. 동시 확인·기록 쓰기·비밀번호 변경과 삭제의 잠금/경쟁, 삭제 후 기존 다른 세션·복구 토큰으로 사적 자료 조회/계정 부활0.
6. migration upgrade/downgrade의 기존 자료 보존·실제 OpenAPI 생성·전체 회귀·정적 검사·P1/P2 리뷰·최신 diff/충돌/체크 게이트.

모의 메일과 실제 SMTP 도착을 구분한다. 웹 화면·실제 Chrome·운영 적용·전체4단계·1~6단계 통과는 이 API Story의 결과에 포함되지 않는다.

## 실제 구현과 잠금 보완

탈퇴 전용 `account_withdrawals`는 계정당1행이며 challenge/코드는 목적별 HMAC, 세션은 SHA-256, credential version을 저장한다. 새 요청은 기존 확인을 대체한다. 실제 SMTP 코드에는 가입/복구와 다른 탈퇴 제목·본문을 적용했다. 시험 의존성을 비시험 서버에 주입하면 시작을 거부한다. 코드/확인값은 브라우저 메모리·별도 웹 Story에서만 연결하고 이 API PR에는 웹 버튼을 넣지 않았다.

구현에서 기존 reset handler가 최초 protect로 요청 세션을 먼저 잠근다는 사실을 확인했다. 위 초기 user→session 구상만으로 안전하다고 가정하지 않았다. 실제 적용은 user NO KEY UPDATE→**본인 모든 세션 NOWAIT**→현재 세션 재검증→전용 proof 잠금이다. 이미 다른 탭/만료 cleanup이 소유한 세션은 건너뛰지 않고503/rollback한다. 사용자 행 등 나머지 대기는 transaction-local2초 lock_timeout으로 제한한다. 코드가 맞아도 잠금 충돌이면 삭제0이며 사용자 명시 재시도만 허용한다. 가입 확인 행도 NOWAIT 재검사하고 user cascade 뒤 이메일별 quota와 최신 가입 잔여 상태를 제거한다. 기존 인증 handler의 순서를 광범위하게 바꾸지는 않았다.

메일 발송 중에는 bounded SMTP timeout10초와 기존 공유 메일 제한을 유지한다. 가입·복구·탈퇴를 합쳐 이메일당 시간당5회/전송 peer당20회이며 실패 발송도 소모한다. quota INSERT와 SELECT 사이에 실제 삭제가 일어나는 경우 제한 행 재생성을 최대3회 시도하고 해결되지 않으면503이다. 이 재시도는 **보안 제한 행**에만 적용하고 계정 DELETE에는 적용하지 않는다.

새0005 migration에는 전용 proof와 sessions owner/Google flow session FK 조회 인덱스를 추가했다. 이전0001~0004 파일은 그대로다. 남은 proof가 있으면 downgrade를 거부하고, 합성 proof만 제거한 실제 downgrade/upgrade에서 기존 계정·수행 기록이 보존됨을 확인했다. 운영 migration은 실행하지 않았다. 아직 커밋되지 않은 migration 수정본의 빈 스키마 적용까지 확인하려고 별도 소유 Unix socket/55440 DB를 만들었고 이전55439 시험 DB·파일은 보존했다.

## 최종 로컬 통과 — 2026-10-05

전체 실제 HTTP/SQL242건이58.28초에 통과했다(실패0/오류0/skip0). 원본은 backend-regression-verified.xml이며 새 전용37건과 기존205건을 포함한다. 기존 uvicorn 경로의 asyncio deprecation 경고1건은 보존했으며 운영 장애나 통과 기준으로 세지 않는다. DOM279건 단일 worker·실제 타입 생성 두 번의 SHA-256 동일성·Biome79파일/TypeScript·Ruff25파일/mypy7파일·production 빌드/개발 진입 차단 검사·git diff --check가 통과했다.

작성자의 범위별 리뷰에서 인증/소유권·원자성·실제 경합·새 migration 자료 보존과 인덱스를 점검하고 이 Story 범위의 미해결P1/P2는 없다. 독립 리뷰/의료 전문가 승인·실제 공급자·운영 DB·HTTPS 배포 완료를 의미하지 않는다. 다음은 최신 main의 새 브랜치에서 **S4.6 계정·탈퇴 웹**을 같은 화이트·블루 디자인으로 구현하며, 취소/오류/불확실 결과·기존 세션 이탈까지 실제 Chrome으로 검증한다. 전체4단계·1~6단계·출시 후보판은 미완료다.

staged diff 검사에서 원본 실패 traceback의 줄 끝 공백이 검출됐다. 읽기용 XML만 줄 끝 공백 정규화하고 원본 전체 바이트는 같은 이름의 .xml.original.gz로 보존했다. 복원 일치·원본 SHA-256과 실패 이력을 증거 README에 기록했다. 기존 아바타 자료나 기존 검증 실패를 폐기하지 않았으며 제품 기준/결과 수는 변경하지 않았다.
