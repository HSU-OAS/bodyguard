# S4.3 — 본인 스트레칭 수행 기록 기간 삭제 API

구현·회귀 검증 중 · 선행 main ddcf800(PR #21) · FR-U-05 / FR-U-04

## 범위와 삭제 경계

출시 계약4단계의 본인 데이터 관리 중 현재 존재하는 스트레칭 수행 기록을 사용자가 고른 기간으로 삭제하는 API를 구현한다. 계정 탈퇴·1분 자세 요약·알림·설정 삭제는 별도 Story와 최종 통합에 남기며, 본 Story를 전체 데이터 삭제 완료로 표시하지 않는다.

운영 DB·실제 사용자 기록에는 실행하지 않는다. 하네스가 소유한 격리 PostgreSQL의 합성 데이터만 생성·삭제한다. 원본 사용자 파일·아바타·기존 검증 증거는 그대로 둔다. 새 비용·시크릿·외부 연결·운영 migration은 없다.

## CTO 기술 계약

- `POST /api/v1/records/stretch/delete-preview`: start 포함/end 제외의 aware 기간을 검사하고 본인 소유 기록 수와 서버 cutoff·10분 만료·확인 서명을 반환한다. 기존 잠긴 세션·Origin/CSRF를 사용한다. 날짜/영상/좌표/임의 user_id를 덧붙이는 payload를 허용하지 않는다.
- `POST /api/v1/records/stretch/delete`: preview의 기간·cutoff·만료·count·서명과 고정 확인문 `delete-stretch-records`를 받는다. 서명은 현재 본인 인증 세션·서버 키의 목적별 HMAC으로 검증한다. key·쿠키·user_id를 응답에 넣지 않는다.
- cutoff 이후 저장된 기록은 종료 시각이 선택 기간에 들어오더라도 삭제하지 않는다. 미리보기는 대상 전체의 지문(fingerprint)도 서명한다. 대상 확인과 삭제를 하나의 SQL 문장으로 묶으며, 비어 있지 않은 대상의 수 또는 내용이 달라지면409로 재확인을 요구하고 삭제하지 않는다. 이미 삭제되어 대상이 비어 있는 동일 확인 재전송은 삭제0으로 안전하게 응답한다. 같은 시각에 추가 저장된 기록도 지문 변경으로 보호한다.
- start<end, timezone/형식·cutoff/만료 일관성, 현재 시간과 만료를 검사한다. 위조/타 계정/다른 인증 세션의 확인은403, 정상 서명의 만료는409로 재확인을 안내한다. 오류 원문·서명을 반사하지 않는다.
- 삭제는 본인·기간·created_at≤cutoff를 모두 만족한 행만 단일 transaction에서 적용하며 실제 삭제 수만 응답한다. 읽기 전용 GET·preview·미확인 요청으로 행을 삭제하지 않는다. 서버 기록을 직접 삭제하므로 제품 화면은 후속 Story에서 복구 불가와 정확한 범위를 명시하고 취소/확인 단계로 연결한다.
- 서버 인증 키/기존 세션 경계를 재사용하며 별도 영구 토큰/원시 데이터 저장은 추가하지 않는다. 이는 이미 승인된 사용자 요청 삭제의 기술 구현이며 보존·법무 정책 확정이나 운영 적용 승인이 아니다.

## 수용 하네스

실제 격리 SQL/HTTP로 다음을 검증한다.

1. 본인 preview→명시 확인→선택 기간 삭제, 다른 기간·계정·세션은 보존.
2. preview만/잘못된 확인/Origin·CSRF 없는 요청은 삭제0.
3. cutoff 뒤 생성한 과거 종료 시각 기록 보존, 같은 확인 재전송의 추가 삭제0.
4. 기간·count·cutoff·서명 위조/다른 계정·새 세션 재사용 거부, 만료409.
5. invalid/naive/숫자 timestamp·역순·unknown 필드의422, 원문 오류 비반사.
6. 실제 OpenAPI 타입 생성, 전체 backend/frontend 회귀·정적 검사·diff 리뷰. 삭제 화면/실제 Chrome 삭제 흐름은 다음 웹 Story로 구분한다.

명세와 시험 작성은 검증 통과가 아니다. 다음 구현에서 red를 green으로 바꾸고 실제 실패·보완·미실행을 기록해야 PR 게이트를 진행한다.

## 최초 실제 실행 — red

보호된 격리 PostgreSQL18.6에서 새 실행 하네스3건을 돌렸다. 기존 기록 저장은201이고 삭제 preview POST는 미구현405여서3건 모두 실패했다. 삭제/보존/서명 기준을 통과했다는 증거가 아니며 실제 삭제는 수행되지 않았다. 테스트 역할의 합성 기록만 사용했고 운영/사용자 데이터와 기존 파일·증거는 건드리지 않았다. 다음 작업은 preview와 확인 API 구현 및 수용 기준의 실제 green 검증이다.

## 구현과 실패 보완 기록

실제 PostgreSQL/HTTP에서 삭제18건과 기존 기록19건을 함께 실행해37건 통과했다. 본인 확인 삭제, 같은 시각의 신규 기록 재확인, cutoff 뒤 저장 보존, 다른 계정·새 세션·위조 거부와 실제 동시 확인의 삭제1/재전송0을 검증했다. 삭제 화면과 실제 사람 수행은 이 결과에 포함되지 않는다.

전체 프런트엔드 회귀의 첫 실행은241통과/1실패였다. 기록 목록의 로딩 화면이 fetch 시작보다 먼저 표시되는데 테스트가 아직 설정되지 않은 응답 함수를 호출해 빈 결과가 도착하지 않았다. 대기 중인 실제 mock 요청이 존재하는지 확인한 뒤 응답하도록 하네스를 수정했다. 빈 화면 기준이나 제품 코드는 낮추거나 변경하지 않았다. 재실행은242건 통과이며 TypeScript/production 빌드도 통과했다. 이는 모의 DOM 회귀이고 실제 브라우저 삭제 검증은 후속 웹 Story에서 수행한다.

전체 backend197건을 실제 격리 DB로 실행해 통과했다(기존 비밀번호 복구에서 Python3.16 예정 deprecation 경고1개). 이어서 확인문·bool count·naive cutoff·숫자 만료·추가 user_id/영상 거부와 빈 기간·시작 포함/끝 제외를 추가했고 삭제25건 전부 재실행 통과했다. 전체197 실행은 이 추가7건 이전의 결과로 구분한다. Ruff check/format, mypy app, Biome, TypeScript, production 빌드와 후보/미연결 엔진 번들0 검사 통과다. DB·HTTP·동시 요청은 실제이고 사용자 기록은 합성이다. 운영 부하/실제 참여자·실제 공급자·실제 브라우저 삭제는 이 검증에 포함되지 않는다.

리뷰: 서명은 계정·현재 세션·전체 기간/대상/만료를 연결하며, 대상 잠금과 비교·삭제는 동일 SQL 문장에 묶인다. 잠금은 ID 순서로 고정한다. 범위 내 미해결 P1/P2는 없지만, 큰 기간의 집계 비용·운영 요청 제한/부하 검증은5~6단계 출시 게이트에 남는다. 화면은409를 자동 삭제 재시도로 처리하지 않고 새로운 미리보기·명시 확인으로 연결해야 한다. 현재 전체 데이터 관리나 출시 완료를 뜻하지 않는다.
