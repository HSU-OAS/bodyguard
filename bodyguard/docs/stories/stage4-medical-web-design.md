# S4.D — 화이트·블루 웹 디자인 기준

2026-10-05 · 로컬 검증 통과 / PR 게이트 · 최신 main143090b에서 독립 Story 시작

## 요청과 범위

CEO가 의학 계열의 전문적인 화이트·블루 웹 디자인과 web-design-studio 사용을 지정했다. BODYGUARD는 노트북 브라우저 웹이며 설치형·네이티브 앱이 아니다. 기존 React 구조, 문구, 인증·기록·개발 전용 코칭 경계를 유지한다.

현재 소개·로그인·시작·탐색·기록에 남은 청록색을 공통 토큰으로 교체한다. 아바타·판정·백엔드 제품 코드·DB·배포·외부 폰트·새 UI 라이브러리는 변경하지 않는다. 아직 검증되지 않은 코칭과 아바타를 공개하거나 의료기관 인증·진단 효과를 꾸며 넣지 않는다.

## 디자인 계약 (FR-V-01 / FR-U-04 / NFR-08)

- 바탕은 백색, 제목은 짙은 네이비, 본문은 읽기 쉬운 청회색. 주 행동·링크·선택·초점만 동일한 블루를 사용한다.
- 입력 테두리와 선택 상태는 충분한 대비를 갖춘다. 구분선은 조용하게 유지하고 삭제·오류의 의미 있는 적색과 공식 Google 버튼 규칙은 보존한다.
- 기존 제목·본문 위계와 시스템 한글 글꼴을 유지하되 16px × 1.25 역할 토큰, 입력/버튼8px·안내12px 라운딩으로 정리한다. 헤더 메뉴는 좁은 창과 확대에서 줄바꿈하며 페이지 가로 스크롤을 만들지 않는다. 기록 표 자체의 가로 스크롤은 허용한다.
- 키보드 초점은 3px 선과 간격으로 표시한다. 버튼 색상 반응만 120ms이며 reduced-motion에서는 즉시 전환한다. 장식적인 움직임·유리·3D 대체 그림은 추가하지 않는다.
- 흰색·청색 디자인은 서비스 분위기이지 의료 자격·검증 완료를 의미하지 않는다. 안전 안내와 준비 중 상태를 그대로 유지한다.

## 수용 기준 / 하네스

1. 공통 토큰을 실제 CSS에서 읽어 본문·보조문구·파란 버튼·선택·오류는 텍스트 대비4.5:1 이상, 입력 테두리·초점은3:1 이상으로 계산한다.
2. production Chrome에서 소개·로그인·가입·복구·실제 가입 후 시작·탐색·기록의 계산 스타일, 주 행동, 빈 상태와 키보드를 확인한다.
3. 1440px·700px·375px 및 로그인 CSS zoom200%에서 실제 화면을 확인한다. CSS zoom은 실제 브라우저 확대와 구분하고, 375px는 좁은 웹 창의 스트레스 시험이며 모바일 서비스 지원을 추가하지 않는다.
4. 실제 API/격리 SQL로 가입·잘못된 코드·성공·기록 목록/상세/삭제를 재실행한다. 지연과 연결 실패는 명시적인 시험 주입이며 실제 외부 장애로 표시하지 않는다.
5. 브라우저 스크린샷을 직접 확인하고 visual-audit, hierarchy-principles, spatial-rhythm, craft-signals, color-systems, type-systems, motion-design, quality-checklist로 구체적인 최종 비평을 남긴다.
6. 전체 DOM 회귀·정적 검사·타입·production 빌드·공개 후보 차단·git diff --check를 실제 실행한다. 실패와 재실행을 구분해 보존한다.

## 스킬 적용

web-design-studio의 직접 코드/실제 화면 조사 → frontend-design 계약 → UI UX Pro Max의 대비·키보드·React 폼 점검 → 실제 브라우저 → 8개 비평 스킬 순서다. 첫 자동 추천의 Neumorphism·청록·초록 CTA·후기는 제품과 맞지 않아 채택하지 않았다. 의료 블루 색상 검색으로 좁혀 참고하되 기존 시스템을 유지한다. Figma·외부 폰트·새 자동 훅은 사용하지 않는다.

## 실제 진행 / 미완료

- 최초 오프라인 설치는 @vitejs/plugin-react 캐시 부재로 실패했다. 잠금 파일을 바꾸지 않고 기존 의존성의 일반 설치를 재시도한다.
- 토큰 초기14건 실패(기존 청록·토큰 없음)를 보존했고 수정 후14건 통과했다.
- 첫 전체 DOM은276통과/3실패(기존 시제품·선택의5초 시간 초과2건, 기록 삭제 미리보기 대기1건)다. 빌드/브라우저 준비와 겹친 실행이며 원인을 단정하거나 검증 통과로 세지 않는다. 소스/기준을 바꾸지 않은 단독 전체 재실행으로 확인한다.
- 첫 실제 Chrome은2통과/1실패다. 추천 버튼 클릭 후 포인터가 남아 hover 색을 정상 색과 비교한 시험 오류였다. 실제 화면은 정상/hover 두 블루를 사용하며 포인터를 옮겨 상태별로 확인하도록 하네스를 수정했다. 빈 기록 문구의 잘못된 시험 기대값도 기존 구현 문구와 일치시켰다. 실패 스크린샷·보고서는 보존한다.
- 스킬 비평에서 기존 글자 크기·라운딩의 잔여 차이를 찾아 공통 비율·8/12px로 정리했다. 최종 실제 화면 검증은 진행 중이다. 디자인 Story 완료가 Stage2/3/4 또는 1~6단계 완료를 뜻하지 않는다.

## 최종 실제 검증

- 단독 DOM도278통과/1실패, 3파일 진단24통과/2실패, 삭제 단독10통과, 변경 전 main 소스의 삭제 단독10통과를 각각 보존했다. 단순 부하라고 단정하지 않았다.
- 미리보기 대기를3초로 늘린 진단도278통과/1실패였다. 이 변경은 되돌렸다. AbortSignal 진단은 실제 취소된 요청을 검출해278통과/1실패했다. StrictMode의 첫 DOM commit에서 누른 가짜 클릭과 mount passive-effect cleanup의 경합이었다.
- 하네스는 기록 목록이 준비된 뒤 클릭하고 요청이 취소되지 않았음을 검사한다. 제품 코드·기본1초 findBy/5초 test 대기·API15초 제한·실제 판정 기준은 변경하지 않았다. 이후 전체279건을15.46초와15.21초에 연속 통과했다. 모의 DOM 검증이며 실제 SQL 검증과 구분한다.

- 최종 기록 Chrome11흐름 통과(30.6초): 실제 API/SQL의 조회·상세·기간·페이지·취소·명시 삭제·만료·대상 변경·다른 계정/늦은 응답 보존. 다른 테스트와 DB를 공유하지 않은 Unix-socket 시험 DB다.

- 실제 최종 소개·로그인 초점·탐색375px·빈 기록·삭제 확인700px 스크린샷을 직접 보았다. [증거와 최종 비평](../review/medical-web-design/README.md).
