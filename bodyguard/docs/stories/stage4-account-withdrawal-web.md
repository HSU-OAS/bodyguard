## 범위·의존성

S4.5 API는 PR #25/merge20dcefc로 실제 main 포함·소스 브랜치 보존을 확인했다. 최신 main의 `codex/stage4-account-web`에서 한 목적의 PR로 계정 관리·본인 이메일 재확인 탈퇴 화면을 연결한다. CEO 지정 web-design-studio를 사용하고 기존 [화이트·블루 디자인 계약](../web-design.md)을 유지한다. 제품은 설치형 앱이 아닌 브라우저 **웹**이다.

별도 승인 없는 실제 SMTP/Google, 운영 계정 삭제·DB migration·시크릿·배포·출시·개인정보/보관 정책 확정은 제외한다. 합성 메일·격리 PostgreSQL/실제 HTTP/production Chrome으로 검증한다. 이월 아바타의 같은 부위 수정 사이클을 새로 시작하지 않는다. Stage2·실제 코칭·전체4단계/1~6단계 완료가 아니다.

## 화면·상태 계약

- `/account`: 검증된 이메일, 수행 기록 관리 링크, 로그아웃, 별도의 회원 탈퇴 진입. 기본 관리와 위험 작업을 분리하며 미구현 설정을 작동하는 기능처럼 나열하지 않는다.
- `/account/delete`: 현재 본인 이메일, 계정·수행 기록 삭제 및 복구 불가 안내 → 인증 코드 요청 → 코드와 `탈퇴` 명시 입력 → 최종 삭제 버튼 → 실제204일 때만 완료. 전송·잘못된 입력·취소·재발송은 삭제하지 않는다.
- 취소·이탈은 확인 요청 없이 계정으로 복귀한다. 진행 중 화면은 중복 제출을 즉시 차단한다. 최종 요청 중 다른 사적 화면은 닫고, 전용 화면은 세션 상태 변경으로 해제하지 않아 응답을 끝까지 처리한다.
- 확인값·코드·동의문은 메모리에만 유지한다. 라우트 이탈·계정 변경·취소에서 폐기하고 늦은 응답을 재사용하지 않는다. GET/뒤로가기/재조회에서 삭제를 자동 실행하지 않는다.
- 응답 단절·5xx·잘못된 성공 상태는 완료로 표시하지 않는다. 확인값을 폐기하고 계정 상태 재확인/재로그인을 제공한다.401만으로 삭제 완료를 추정하지 않는다.400/422/429 뒤에도 새 `/me`로 계정 경계를 재확인하고 캐시된 사용자로 사적 화면을 되살리지 않는다.
- 새 발송은 기존 확인값을 교체한다. 오답·만료는 올바른 코드/새 발송을 안내하고 요청 제한은 Retry-After 대기 시간을 표시한다. 코드 자동 제출·자동 삭제 재시도는 없다.

## 디자인 계약

주요 작업은 계정 관리와 신중한 탈퇴다. 기존 흰 배경/블루 CTA/잉크 텍스트·system Korean font·4px 간격·48px 제어·8px radius를 재사용한다. 외부 폰트, 새 디자인 시스템, 장식용3D, 진단/전문 자격/효과 보증은 추가하지 않는다. 일반 작업은 블루, 최종 삭제만 기존 danger 색이다. 단계별 제목·알림·포커스로 읽는 순서가 자연스럽게 이어지게 한다. 의료 서비스다운 정돈된 인상이지 의학적 검증을 가장하는 화면이 아니다.

UIUXProMax 검색의 첫 일반 추천은 랜딩/Neumorphism이라 채택하지 않았다. 좁혀 재검색한 Minimalism 권장은 기존 체계와 맞는 여백/위계만 참고하며 orange CTA·외부 Fira 폰트·히어로는 적용하지 않는다. 파괴적 작업 명시 확인과 비동기 오류 처리만 현재 React 구조에 맞게 적용한다.

## 실제 구현·완료 증거

내 계정 메뉴와 `/account`의 이메일·기록 관리·로그아웃·탈퇴 안내를 연결했다. 탈퇴 화면은 코드 전송만으로 삭제하지 않고6ASCII 코드와 명시 “탈퇴” 입력 후 한 번만 최종 요청한다. 확인값은 엄격한202/43ASCII 계약이며 실제204만 완료다. 중앙 인증 상태 `withdrawing`은 다른 사적 경로를 닫되 이 전용 화면은 해제하지 않아 확인 요청을 불필요하게 중단하지 않는다.400/422/429는 새로운 `/me` 결과가 같은 계정일 때만 입력 수정이 가능하며 캐시 계정 복원은 없다. 이탈의Abort/늦은204·다른 계정 재확인·연결 실패는 사적 화면을 되살리지 않는다.

production Chrome에서 가입한 합성 계정의 기록 저장→취소 후 보존→오답/만료 보존→명시 탈퇴204→기존 별도 세션 접근 거부·타 계정 보존을 실제 확인했다. 같은 브라우저의 다른 열린 계정 탭도 BroadcastChannel 후 새 `/me` 확인으로 로그인 화면으로 이탈했다. 서버 DELETE 전/후 응답 단절을 별도 시험하고 자동 삭제 재시도0·완료 추정0을 검사했다. 실제 메일은 합성 IPC, 만료는 시험 시계601초이며 실제 SMTP/10분 대기라고 표시하지 않는다. 전송503/429 UI 상태는 주입된 오류이며 API의 실제 실패 SQL 검증과 구분한다.

최종 DOM322건/26파일·실제 API/SQL242건·Chrome 탈퇴6흐름/기록11흐름/공통 디자인3흐름·TypeScript·Biome86파일·Ruff26파일/mypy app7파일·production 빌드·DEV 후보/미연결 코칭 엔진0·diff 검사를 실제 실행했다. production JS314.04kB(gzip96.35)/CSS26.36kB(gzip6.49)이며 노트북 코칭·아바타 성능의 증거는 아니다. 실제1440/768/375·키보드·대비·동작 감소·light 계약과 오류/완료 PNG를 [원본·실패·화면 검수](../review/stage4-account-web/README.md)에 보존한다. 최초 red/확장 하네스 실패/정적 오류/시험 서버 준비 실패를 숨기지 않는다.
