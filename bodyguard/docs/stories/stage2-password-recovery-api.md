# S2.6a1 — 비밀번호 복구 API

2026-10-01 · 진행 중 · 기준 main `4d5e319`. FR-U-03, NFR-08, design §13.3~4, [사전 승인 운영 규칙](../operating-rules.md)을 따른다. S2.3b 사람 수행/실제 Gmail 승인 대기 중 가능한 독립 작업이다.

## 범위와 경계

기존 CSRF·HttpOnly 세션·이메일 정규화·Argon2id·PostgreSQL 제한 카운터·SMTP를 재사용한다. 새 복구 토큰 테이블과 자격증명 버전을 **새 migration**으로 추가한다. 기존 migration은 변경하지 않는다. 링크는 설정의 검증된 Origin만 쓰고 fragment 토큰을 웹의 후속 S2.6a2에서 메모리에 받아 지운다. Host/외부 next/URL query를 신뢰하지 않는다.

API 구현/하네스 PR이며 복구 화면은 후속 Story다. 실제 Gmail·구글·외부 계정/시크릿·운영 migration·배포는 실행하지 않는다. 실제 전달 시험 미완료를 숨기거나 2단계 통과로 표시하지 않는다.

## CTO 보안 결정

- 요청은 가입 여부와 관계없이 같은 202·안내다. **요청 접수이지 메일 배달 확인이 아니다.** 등록된 주소에만 native BackgroundTasks로 전달한다. SMTP 미설정은 모든 주소에 동일 503, 발송 중 실패한 토큰은 폐기한다. 반복 요청 제한/재요청 안내와 실제 Gmail 수신 검증이 별도로 필요하다. UI에서 미전달 요청을 '메일 발송 성공'으로 표현하지 않는다.
- native background 전달은 프로세스 종료 시 유실될 수 있다. 30분 일회용 토큰·재요청으로 복구하며 내구성 큐/새 서비스는 추가하지 않는다. 실제 운영 부하/장애 시험에서 필요하면 전달 상태·내구성 outbox를 별도 검증한다.
- 토큰은 32바이트 난수, DB는 SHA-256만 보관한다. 마지막 DB 발급 링크만 유효하며 동시 배경 작업/메일 전달 순서는 보장하지 않는다. 교체/유실/만료 시 다시 요청한다. 30분 경계에서 만료, GET/잘못된 비밀번호/위조 토큰은 소비하지 않는다.
- 재설정 요청만으로 로그인/비밀번호를 바꾸지 않는다. 성공 시 비밀번호 변경·토큰 소비·자격증명 버전 증가를 동일 transaction으로 처리한다. 이전 버전 세션은 전부 무효이고 자동 로그인하지 않는다.
- 자격증명 버전은 reset과 동시에 시작한 이전 비밀번호 로그인도 새 유효 세션을 남기지 못하게 한다. 로그인 시 실제 검증한 비밀번호의 버전을 세션에 붙이고 모든 유효성 검사에서 현재 버전과 대조한다. 단순 기존 세션 일괄 UPDATE는 경쟁 로그인 누락/서로 다른 세션의 잠금 교착 위험이 있어 쓰지 않는다.
- 잠금 순서는 세션 → 사용자 → 복구 행이다. 토큰을 잠그기 전 사용자 식별자를 읽고, 사용자 잠금 후 토큰/만료를 다시 검사한다. 배경 발급도 사용자 → 복구 순서다.
- 이메일/IP의 기존 메일 제한 5/20회·시간을 공유한다. 복구 소비는 IP당 30회/분 제한한다. 기준은 기술 기본값이며 실제 카메라 판정 수치와 무관하다.

근거: [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)의 가입 여부/응답시간 노출 방지·안전한 난수/보관·일회용·안전한 링크·자동 로그인 금지·기존 세션 무효화. API 접수 이후 비동기 전달, fragment 링크와 버전 방식은 이 코드베이스에 적용한 기술 결정이다.

## 계약·수용 기준

| API | 성공 | 오류 |
|---|---|---|
| POST /api/v1/auth/password/forgot | email → 202, 일반 요청 접수 안내 | 403 CSRF/Origin, 422 입력, 429 제한, 503 설정/DB |
| POST /api/v1/auth/password/reset | token/password → 204, 자동 인증 없음 | 400 위조/소비/만료, 403 보호, 422 입력, 429 제한, 503 DB |

| ID | 실행형 하네스와 통과 기준 |
|---|---|
| R-01 | 실제 DB 기존/없는 주소의 같은 HTTP 상태/본문·없는 주소 미발송, 배경 전달 전 응답 시작 |
| R-02 | 최신 링크만 유효·30분 경계·일회용/병렬 소비 한 번·해시 보관·타인 계정 영향 없음 |
| R-03 | 새 비밀번호 Argon2id·정규화/길이 경계·옛 비밀번호 거부·모든 옛 세션/CSRF/경쟁 로그인 차단·자동 로그인 없음 |
| R-04 | 기존 Origin/CSRF·메일/IP 요청/소비 제한·재기동/위조 헤더·메일 실패/설정 누락·토큰/비밀번호/시크릿 출력 금지 |
| R-05 | 새 migration upgrade의 기존 데이터/세션 보존·제약, downgrade는 인증 세션 폐기 후 버전 제거(옛 세션 부활 금지), 실제 API/SQL 기존 회귀·생성 OpenAPI 타입·프런트 빌드 |

PostgreSQL 18의 격리 DB/별도 연결·실제 FastAPI를 사용한다. 시간/메일은 통제된 시험 장치이며 실제 Gmail 도착이나 production 장애 검증으로 세지 않는다. API 브라우저 회귀는 실제 로컬 HTTP/SQL과 production 웹을 사용하지만 아직 복구 화면은 없다.

## 결과

로컬 구현·필수 검증을 통과했다. 최초 실제 DB red는 미구현 forgot의 404였다. 65개 기본 회귀 → 87개 복구 경계 → 리뷰 보완 후 **90개 실제 FastAPI/PostgreSQL 검사 통과(22.95초)**다. 길이 검사 실패 한 건은 '짧은' fixture가 실제 22자여서 발생했고 13자로 고쳐 재실행했다. 입력 기준을 완화한 것이 아니다.

- R-01은 등록/미등록의 같은 HTTP 응답과 미등록 미발송, DB 해시를 검사했다. 별도 소유 ephemeral listener·Uvicorn·실제 httpx HTTP에서 시험 전달을 잠근 동안에도 202 응답이 도착함을 확인했다. SMTP 자체/외부 수신 검증은 아니다.
- R-02/03은 1799.999/1800/1800.001초 경계, 교체·재사용·GET·형식 오류, 두 독립 연결의 동시 소비 `204/400`, 타인 계정 유지·모든 옛 쿠키/CSRF 차단을 검사했다. 옛 비밀번호 검증을 잠근 로그인과 실제 재설정을 교차했고, 옛 버전으로 뒤늦게 발급된 세션의 /me는 401이었다. 재설정 단독 사용 시 자동 인증 없음·새 비밀번호 로그인과 Argon2id도 확인했다.
- R-04는 기존 Origin/CSRF, 설정 미연결의 양쪽 503, 모의 전달 실패의 일반 접수/토큰 폐기, 공유 메일/소비 제한·재기동, Host 링크 주입, 비시험 메일 fixture 차단, 형식 오류 민감값 미반사를 검사했다. 제어된 DB 소비 실패를 주입해 실제 transaction의 비밀번호/버전/토큰 rollback과 재시도도 통과했다.
- R-05는 **격리 DB에서만** 실제 downgrade/upgrade와 구 v1 SQL의 시험 계정/세션을 검사했다. upgrade의 데이터/세션 보존·NULL 버전 제약, downgrade의 인증 세션 폐기를 확인했다. 기존 운영 DB에서 실행한 것이 아니다.
- 실제 API·격리 PostgreSQL·production Chrome 계정 회귀 9개(실제 60초 재발송 포함) 통과. 사람 없는 시험 카메라·실제 MediaPipe/Chrome 시작/중지/재시작/이탈 회귀 1개 통과. 복구 UI/실제 사람 검사와 구분한다.
- 실제 OpenAPI 타입 재생성, Biome/TypeScript/production build, Vitest 82개, Ruff 검사/형식, mypy 앱 5파일을 실행했다. 최초 타입 생성은 uv 캐시 권한으로 실패했으며 같은 기존 명령을 필요한 캐시 권한으로 재실행해 통과했다. 잠금파일/의존성 버전 변경은 없다.

리뷰에서 역행 시 자격증명 버전 제거가 옛 세션을 부활시킬 위험을 발견해 인증 세션 폐기를 먼저 추가하고 실제 DB로 재검증했다. 비시험 가짜 전달 주입/Host 링크/중간 DB 실패 보완도 통과했다. API 범위의 미해결 P1/P2는 없으며 Git/PR 최신 diff·체크·충돌 게이트는 병합 직전에 다시 확인한다. Starlette httpx와 asyncio의 upstream deprecation 경고 2개는 시험 실패가 아니며 새 의존성 추가로 우회하지 않았다.

S2.6a2 복구 화면/링크 fragment 지우기·메모리 관리·접근성·API 브라우저 복구 흐름이 다음 독립 Story다. 실제 Gmail 수신·Google·S2.7은 미완료다. 실제 Gmail 연결 승인 요청 범위는 기존 가입 인증메일 최대 3통이므로 복구 실메일은 그 승인에 임의로 포함하지 않는다. 아바타 Draft PR #9의 P2와 S2.3b/2단계 게이트도 이 Story로 해소되지 않는다.
