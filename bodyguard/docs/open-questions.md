# Bodyguard — 아직 정하지 않은 것

2026-09-26 기준, 첫 출시 결정은 2026-09-29 갱신 · Git 승인 규칙 정합화 2026-10-01 · 근거: `research/01_사용자요구사항_원문.md`, 과목 산출물(차터·PRD·WBS), `release-plan.md`

> 문서를 쓰면서 **사용자에게 확인받지 않은 것**을 전부 여기에 모았다.
> 다른 문서에서 `[미정 Q-05]`처럼 보이면 이 목록의 항목이다.
> `PO 제안`은 문서를 쓰면서 정한 기본값이다. 사용자가 고르거나 고치기 전까지는 **확정이 아니다.**
> 정해지면 맨 아래 "결정된 것"으로 옮기고 prd·design·ADR에 반영한다. 번호는 다시 쓰지 않는다.

---

## 먼저 정해야 하는 것

첫 출시 계약 정합화와 시제품 실험은 진행할 수 있다. 그러나 검증되지 않은 동작의 자동 판정, 외부 결제·배포, 사업상 개인정보 문구는 해당 근거와 승인이 갖춰지기 전까지 진행하지 않는다.

| 시점 | 항목 |
|---|---|
| 판정 엔진 만들기 전 | Q-05 지표 정의 · Q-06 임계값 — 실측(M-3, M-4) 후에 정한다 |
| 사용자 테스트 전 | Q-04 배포 위치 |
| 해당 기능 전 | 나머지 |
| 개발 막바지 | Q-26 개인정보 동의·처리방침 (보류) |
| 실측으로 정할 것 | M-1 ~ M-5 |

**판정 기준(몇 도부터 주의·이탈로 볼지)은 아직 숫자가 없다.** 판정 3단계와 색은 정했지만(원문 43) 숫자는 실측 데이터로 정해야 한다.

## 1. 배포

### Q-04 배포 위치와 도메인
- 왜: 브라우저는 **HTTPS 페이지에서만 카메라를 켜 준다.** localhost는 예외라 개발 중에는 상관없다. 다른 사람이 쓰려면 HTTPS 주소가 있어야 한다. 비밀번호 재설정 메일의 링크도 이 주소를 쓴다
- 막히는 작업: tasks #33, 사용자 테스트
- PO 제안: 없음. 후보만 적는다 — 프런트는 정적 호스팅, 백엔드와 PostgreSQL은 컨테이너 호스팅 (ADR-0015)
- 비용이 드는지, 학교 지원이 있는지 확인이 필요하다

## 2. 판정 규칙

### Q-05 지표 3종을 정면 카메라에서 어떻게 재나
- 왜: 차터의 지표 이름 "목 전방 경사각"과 "상체 전방 굴곡각"은 **옆에서 본 각도**다. 노트북 웹캠은 정면에서 찍는다. 정면 영상에서 이 두 각도는 그대로 나오지 않는다. 어깨 좌우 기울기만 정면에서 바로 잴 수 있다
- 막히는 작업: tasks #6, #7. 판정·알림·스켈레톤 색·기록이 전부 이 값을 쓴다
- 후보: `design.md` §5
  - 목: MediaPipe 깊이값(z) 각도 / 귀·어깨 2D 지수 / 얼굴·어깨 크기 비율(Face Landmarker) / 단안 깊이 모델(원문 40)
  - 상체: 엉덩이가 보이면 깊이값 각도, 안 보이면 어깨가 커지고 내려온 정도
- 고르는 방법: 옆에 폰을 세워 옆모습 각도를 정답으로 동시에 잰다(`design.md` §5.7). 정답과 가장 잘 맞고 가벼운 후보를 쓴다
- 솔직한 전망: 상체 지표는 노트북 웹캠에서 **못 쓸 수도 있다.** 그러면 지표가 2개로 준다. 원래 말씀하신 것도 "2, 3개"였다(원문 10)
- 정할 것: 각도(°)로 보여줄지 지수(%)로 보여줄지, 상체 지표를 뺄지. M-3·M-4 실측 뒤에 정한다

### Q-07 "자세가 5분 넘게 무너짐"을 어떻게 세나

### Q-08 "오래 앉음"을 어떻게 세나

- 전문가 확인: 동작 선정과 유지 시간은 운동·재활 쪽 자료로 한 번 더 확인하는 게 좋다

### Q-10 기준 아바타 판정 색 — 출시 설계 결정
- 기준 아바타는 올바른 수행법을 보여주는 역할이라 사용자 판정 색을 칠하지 않는다. 실제 오류 피드백은 사용자 아바타와 설명에 적용한다
- 확인 불가 부위를 별도 색으로 표시하지 말라는 CEO 결정과 별개다. 필수 관절이 보이지 않으면 내부 통과 판정을 멈춘다

### Q-30 둥근 머리에 판정 색을 어떻게 입히나
- 왜: 스켈레톤 머리를 선 대신 둥근 머리와 얼굴로 바꿨다(원문 55). 목 전방 판정 색은 "머리·목"에 칠하기로 했는데(FR-A-01), 머리 전체를 칠할지 일부만 칠할지 정하지 않았다
- 막히는 작업: tasks #12
- PO 제안: 목 선과 머리 테두리만 판정 색으로 칠하고 얼굴 살색은 그대로 둔다. 머리 전체를 빨갛게 칠하면 얼굴이 무섭게 보이고 눈·입이 묻힌다

### Q-28 내 동작을 따라 움직이는 아바타를 어떻게 만드나
- 확정된 것: **첫 출시**에 사진 기준의 남성·여성 흰색 인체 아바타 두 개가 필요하다. 하나는 올바른 동작, 하나는 웹캠으로 확인 가능한 내 움직임이다. 현재 스켈레톤·MPFB 시제품은 출시 불가다. Blender 모델·리깅·애니메이션 제작도 개발 범위다
- 검증할 것: 단일 노트북 웹캠이 관찰 가능한 관절과 깊이 방향 한계, 리타게팅 방식, 부드러움·지연, 남녀 리그의 같은 동작 품질, 파일 크기·라이선스
- 개인 체형의 정확한 재구성은 확정 요구가 아니다. 그럴듯한 움직임과 실제 판정 정확도를 분리해 검증한다

### Q-29 손 제스처를 제품에서 어디에 쓰나
- 왜: 엄지척 같은 제스처를 인식하게 됐다(원문 53, 54). 지금은 데모에서 표시만 한다
- 정할 것: 예를 들어 스트레칭 시작·건너뛰기를 제스처로 할지, 아바타 표현에만 쓸지
- PO 제안: 없음. 쓰임을 정하기 전까지는 표시만 한다

### Q-11 마네킹 모델과 스트레칭 시범 동작을 어디서 구하나
- 왜: 남녀 모델·리그·기준 애니메이션을 Blender에서 새로 제작해야 한다. 모델·텍스처·동작 데이터의 사용·재배포 권리를 확인해야 한다
- 막히는 작업: tasks #19, #24
- 조건: CC0 또는 CC-BY. 재배포를 막는 무료 에셋은 레포에 넣을 수 없다
- 시범 동작: 정지 자세 몇 장이 아니라 근거에 맞는 시작·진행·목표·복귀가 필요하다. 동작 수와 제작 방식은 근거·촬영 시험으로 결정한다

### Q-12 변화 탐지 기준
- 왜: "평소 범위를 벗어난 구간을 알린다"(차터)만 있다. 무엇을 평소로 볼지 정한 적이 없다

- PO 제안: `design.md` §14 — 측정 60분 이상인 날이 7일 쌓이면 시작한다. 최근 14일과 비교한다. 일별 이탈 비율을 본다. 대시보드에만 표시한다
- 솔직한 전망: 데이터가 하루 한 점이라 PyOD 같은 이상 탐지 라이브러리가 단순 통계보다 나을지 모르겠다. 단순 통계를 먼저 만들고 PyOD와 비교한다
- 재보정 문제: 기준선을 다시 찍으면 편차 값의 기준이 바뀐다. 재보정 전후를 어떻게 이을지도 정해야 한다

### Q-13 리포트 PDF에 무엇을 넣나

- 남은 것: 어느 회사 모델을 후보에 넣을지, 누구 계정·카드로 결제할지, 사용자당 하루 몇 번까지 만들게 할지

## 4. 화면과 사용 흐름

### Q-19 화면 목록
- 첫 출시 필수 흐름: 공개 시작·가입/로그인 → 직접 선택 또는 신체 확인/추천 → 카메라 준비 → 두 아바타 코칭 → 결과·기록. 계정·데이터 관리도 필요하다. 화면별 상세 상태·와이어프레임은 해당 Story 명세에서 확정한다

### Q-32 기존 부가 기능의 첫 출시 포함 범위
- 기존 확정 요구: 5분 자세 이탈·50분 착석 알림, PDF 리포트, LLM 요약, 변화 탐지. 첫 출시에서 임의로 삭제하거나 후속으로 확정하지 않는다
- 할 일: 원문 의도·사용자 가치·단일 웹캠 실현 가능성·비용/운영 의존성을 비교하고 첫 출시 포함 권고안을 CEO에게 제시한다. 외부 LLM 계약·결제·시크릿·배포는 별도 명시 승인이 필요하다

### Q-20 측정 시작과 화면 표시
- 확정된 것: 제품 화면에는 카메라 영상을 보여주지 않는다 (원문 49)
- PO 제안: 접속만으로 카메라를 켜지 않고 "측정 시작" 버튼으로 켠다. 측정 중에는 화면에 항상 "측정 중"을 띄운다. 처음 자리를 맞출 때도 영상 대신 스켈레톤으로 안내한다

### Q-21 알림 방식
- PO 제안: 브라우저 알림과 화면 안 알림을 같이 띄운다. 소리는 설정에서 켠다(기본 꺼짐)
- 브라우저 알림 권한을 거부하면 화면 안 알림만 남는다. 다른 창에서 작업 중이면 못 볼 수 있다

### Q-22 지원 범위
- PO 제안: 데스크톱 크롬·엣지만 지원한다. 한국어만 지원한다. 모바일 브라우저는 범위 밖이다
- 이유: 뒤 탭 동작(M-1)이 브라우저마다 달라서 전부 확인할 여력이 없다

## 5. 운영과 검증

### Q-23 브랜치·리뷰·CI
- CEO 확정(2026-09-29): 최신 `origin/main`에서 Story마다 새 `codex/*` 브랜치, 한 PR에 한 목적, `main` 직접 푸시 금지. 커밋·PR 제목은 `docs: ...`, `feat(web): ...`처럼 목적·범위를 표시하고 본인 계정만 사용한다
- CEO 변경(2026-10-01): [운영 규칙](operating-rules.md)에 따라 합의 1~6단계 Story·커밋·푸시·PR·리뷰 보완·다음 Story를 사전 승인. 필수 검증 통과·미해결 P1/P2 없음·최신 diff/충돌/체크 확인을 충족한 PR 병합도 사전 승인. merge commit·브랜치 유지·CLEAN 확인·체크 없음 표기는 그대로다
- 서버·시크릿·운영 DB migration·배포·비용은 병합과 별도 승인. 읽기·로컬 테스트·PR 재검토는 승인 불필요
- CI 도구는 GitHub Actions로 확정(ADR-0015). 현재 체크는 없으며 도입은 별도 Story로 진행한다. Git 규칙은 더 이상 PO 제안이 아니다

### Q-24 "육안 판정 일치율 80%"를 어떻게 재나
- 왜: 차터의 성공 기준인데 재는 방법을 정한 적이 없다. 영상을 녹화해서 나중에 보면 쉽지만 "영상 저장 안 함" 원칙과 부딪힌다
- PO 제안: 녹화하지 않는다. 옆모습 정답지(`design.md` §5.7)와, 측정하는 동안 옆 사람이 누르는 "나쁜 자세" 버튼을 함께 기준으로 쓴다. 임계값을 맞출 때 쓴 데이터와 일치율을 잴 데이터는 다른 날·다른 사람으로 나눈다

### Q-25 판단이 갈릴 때 우선순위
- PO 제안: 개인정보 → 오판정 방지 → 실시간성 → 기능 (`constitution.md`)
- 9/26 대화에서 기본값으로 말씀드렸고 따로 확인받지는 않았다

|---|---|---|
| M-1 | 창이 뒤로 가도 1초 간격 측정이 되는가 (크롬·엣지) | ADR-0004. 안 되면 "보일 때만 측정"으로 가고, 작업 중 자세 알림은 사라진다 |
| M-2 | 노트북 웹캠에서 몇 fps가 나오는가 (목표 15, 추론 제한 30) | 포즈 모델 크기(lite/full/heavy), ADR-0007 |

| M-4 | 정면 카메라로 목 전방을 잴 수 있는가. 후보 4개를 옆모습 정답과 비교한다 | Q-05 — 어느 후보를 쓸지, 각도로 보여줄지 지수로 보여줄지 |
| M-5 | 켜 두는 동안 CPU·배터리를 얼마나 쓰는가 | 목표 수치가 아직 없다. 깊이 모델을 넣으면 특히 커진다 |

M-1은 특히 불확실하다. 크롬은 뒤로 간 탭에서 화면 갱신(`requestAnimationFrame`)을 멈추고 타이머를 늦춘다. 카메라를 쓰는 탭이 여기서 예외인지는 문서만으로 확신할 수 없어 직접 재야 한다.

M-4의 단안 깊이 모델은 무겁다. 정답과 가장 잘 맞더라도 CPU 부담(M-5)과 같이 보고 고른다.

### 첫 관찰 (2026-09-26 스켈레톤 데모)
- **M-2**: 추론 1회 18.2ms(GPU, lite). 15fps 제한에서 14fps. 목표는 여유 있게 가능하고, 14는 제한 방식을 고치면 된다 → 제한을 30으로 올리고 고르는 방식을 고쳤다 (원문 50)
- **M-2 (30fps로 올린 뒤)**: 30fps, 추론 1회 11.4ms(GPU). 화면 버벅임 없음
- **M-4**: 펀치처럼 손이 카메라 쪽으로 오가는 앞뒤 움직임은 3D 스켈레톤에서 정확히 따라오지 않았다. 정면 카메라에서 앞뒤는 깊이(z) 짐작에 기대기 때문이다. 목 전방도 같은 앞뒤 움직임이라, 깊이값을 쓰는 A안이 약할 수 있다는 신호다. B·C안(화면에서 바로 보이는 크기 비율)과 함께 옆모습 정답지로 비교해야 한다
- **M-3**: 노트북 앞에 앉은 정면 화면에 엉덩이가 아예 들어오지 않았다. 팔꿈치도 화면 밖이었다. 상체 굴곡 A안(엉덩이 기반)은 이 자세에서 쓸 수 없다. B안(어깨 크기·위치)을 실험하거나 지표를 2개로 줄이는 쪽을 먼저 본다
- 화면 밖으로 벗어난 관절도 가시성 0.5를 넘겨 3D에 점으로 나타났다. 가시성만으로는 지어낸 관절을 다 거르지 못한다 → 화면 밖 관절은 쓰지 않게 했고, 필요한 관절이 화면 밖이면 안내한다 (FR-M-07)

## 8. 개발 밖에서 확인할 것

개발 문서에는 영향이 없지만 알고 있어야 하는 것이다.

- **과목 문서와 달라진 점.** 과목 문서는 사람이 관리하므로 건드리지 않았다
  - 저장 범위: PRD·README는 "좌표·각도값을 서버에 적재" → 지금은 1분 요약만(원문 34)
  - 팀장 표기: 차터·README 역할표 맨 위는 "PM 이성수", PRD·WBS는 "팀장 허윤"(원문 22)
  - 알림 조건: PRD는 "정자세 이탈이 이어지면" → 지금은 5분 이탈 + 50분 착석(원문 32)
  - 기준선을 안 찍었을 때: PRD는 "기본 기준값으로 측정" → 제안은 어깨만 판정(`prd.md` §4)
- **사용자 테스트 촬영 동의서**(원문 8). 아직 준비하지 않았다. Q-26과 같이 준비하면 된다
- **레포 Private 전환.** 직접 하기로 했다(원문 36). 조직 설정에 따라 교수님이 레포를 못 보게 될 수 있다
