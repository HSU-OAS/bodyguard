# S3.C5 첫 추론 준비와 GPU 준비 순서 보완

2026-10-17 · [Draft PR #163](https://github.com/HSU-OAS/bodyguard/pull/163) · 이전 source `c0cfe7fabe0ceefecbd35559741ef99d1eca11d9` · **최초 정리 P2 미해결/병합 보류**.

## 사용자 흐름·실제 변경

명시 시작/재개 → 카메라·같은 SDK 소유 → 첫 입력 처리 후 폐기 → 남녀 아바타 GPU 준비 → 다음 새 입력의 코칭 순서로 연결했다. 준비 입력은 아바타 표시·판정·타이머·기록에 전달하지 않는다. 준비 중 종료는 캡처를 즉시 무효화하고 빌린 추론/입력의 해제가 끝난 뒤 SDK·카메라를 회수한다. 새 카메라/SDK나 두 번째 source를 추가하지 않는다.

`ownedPlaybackResources`는 기존 준비 훅의 **명시적 사전 순서 옵션**만 추가했고 기본 호출자의 순서는 유지했다. 기존 목/어깨 실행만 이를 켰다. 준비 실패는 ready가 되지 않으며 cleanup-error를 성공으로 바꾸지 않는다. 모델/화질·필수 얼굴/손·본래5초 응답/종료 제한·임상 판정·API·권한/개인정보·공개 적격0은 그대로다. 기존 원본/GLB·외형·리깅/가중치·화면 구조도 바꾸지 않았다.

## 실패 → 비교 → 실제 적용

- `failure-probe-b`: 실제 SDK/Worker/GLB + Chrome blank fake device를 생성 입력 UI와 함께 실행했다. 첫 흐름 뒤 재개 첫 요청17705ms → `response-timeout`22750ms(기존 마감보다45ms 늦은 타이머) → 늦은 결과22839ms를 확인했다. **직접 실패 경로는 응답 마감 초과**다. 실제 사람/좌표 정확도 검증이 아니다. 최초 native-a cleanup-error의 원인이 같다고 확정하지 않는다.
- 이 실패 runner는 당시 오류 뒤 Chrome 종료 전에 전체 retirement를 기다리지 않았다. 두 번째 SDK ACK/카메라 해제의 관찰이 끝나지 않아 해당 실행의 정리 성공을 주장할 수 없다. 후속 runner는 원래 소유자 해제를 최대11초 관찰하고 그 관찰 상태를 따로 기록한다. SDK5초 제한을 늘린 것이 아니며 관찰 만료를 성공으로 바꾸지 않는다.
- `prewarm-a`: 제품 코드를 바꾸기 전 시험 Vite의 순서만 바꾼 비교. 같은 source의 첫 추론을 아바타 GPU 준비 전에 폐기해 동시 native2흐름/UI4흐름 통과. **이 시험을 제품 구현 증거로 쓰지 않는다.** 당시30개 소스를 실제 before SHA와 대조해 압축 보존했다.
- 실제 구현 후 `actual-native-a` + `actual-browser-a`: 순서 변경용 시험 transform 없이 동시 native2/UI4흐름 통과. `actual-default-a`: 계측을 끈 목 native2흐름 통과. 남녀 어깨 표면/반복 결과/종료/401과 목 회귀도 유지했다. native-a/default-a가 쓴 runner는 이후 프레임 로그 상한 보완 전 정확한 사본을 별도 보존했다.
- `actual-native-final`: 최종 계측에서도 실제 SDK2흐름·두 세대 clean ACK/카메라·GPU 회수와 실패 이벤트0을 확인했다. 프레임 시간 로그를 최초3개로 제한해 제어/ACK26이벤트가 상한에 밀리지 않았다. 단독 시험이며 동시 실행이나 최초 정리 P2 해결의 추가 증거로 확대하지 않는다.

SDK 요청·결과는 **처음3개 시간과 전체 횟수만** 남겨 ACK가 프레임 로그에 밀리지 않도록 했다. Worker 실패는 최대16개 고정 phase/상태/시간 필드만 남긴다. product owner 파일은 시험 Vite에서만 계측하며, 원시 메시지/영상/좌표/예외 내용을 기록하지 않는다. 사전 순서 시험 transform은 실제 구현 뒤 runner에서 제거했다.

## 수용 기준·검수

Given 새 source가 준비 중일 때, When 사전 옵션이 켜졌다면, Then 아바타 factory·ready·scheduler·observe는 열리지 않는다. 준비 완료 뒤 같은 source의 다음 read로 실행한다. Given 준비 중 취소/실패, When 빌린 read가 끝나면, Then source/SDK/카메라는 한 번씩 회수하고 아바타·ready·진행은 없다. Given 기존 기본 호출자, When 사전 옵션이 없으면, Then 이전 준비 순서를 유지한다. 콜백 없는 true/잘못된 옵션은 거절한다.

- 관련 소유자/기존 native adapter/helper: 3파일137검사 통과. 이전 기본 순서 회귀와 새 사전 순서·취소·일반/정리 실패·옵션 경계를 함께 검사했다.
- 전체127파일2095검사, 타입·원래 production build/고지·개발 후보/계측 제외 guard 통과. 변경8코드파일 Biome 오류/info0, 전체471파일 오류0/info17. `git diff --check` 통과.
- 기존 목 실제 Chrome/GLB/오류 표면8흐름 통과. 계정/API는 생성·모의이며 실제 SQL/참여자·물리 웹캠·외부 공급자·컨테이너/HTTPS·운영/배포를 이번에 재검증하지 않았다. 이전 GLB 전체 vertex proof는 보존했으며 새 변형/원본 수정이 없는 이번 작업에서 재실행했다고 세지 않는다.

첫 probe/비교군 명령은 scratch와 label 사이 공백이 빠져 실행 전 경로 assert로 거절됐다. 실패 로그를 보존하고 서로 다른 새 label의 올바른 인자로 실행했다. 첫 복합 runtime patch도 문맥 불일치로 전부 거절됐으며 원문은 터미널에만 있다. 이후 적용한 diff와 실제 회귀만 제품 검증으로 센다. 최초 probe 중간 runner의 완전한 사본은 없고 지문/로그만 보존한다. 11초 관찰 옵션 위치는 실행 전에 Playwright의 세 번째 인자로 맞췄다.

첫 보존 수집기는 이전 manifest의 압축 SHA와 rawSha256 필드를 혼동해 신규 수집 전에 assert로 중단됐다(원문은 터미널). 두 기존 manifest의 각 저장 형식을 구분해 재검증했으며 기존 파일을 수정하지 않았다. 수집기 보완을 제품 검사로 세지 않는다.

code-review 기준으로 새 준비 옵션의 기본 순서 보존, 동일 source/새 stamp, 취소·교체·원본/판정 권한·공개 제외를 작성자 검토했다. 독립 리뷰나 전체 단계 통과가 아니다. 이번 보완은 **관찰한 재개 첫 추론의 마감 초과 경로에 대한 개선**이며 전 환경의 성능 보증이 아니다. 최초 native-a 종료 P2와 기존 Draft/외형·임상/성능 게이트는 남아 Draft를 유지한다. 같은 부하 재현/SDK 해제 원인 보완과 독립 코칭 동작 구현을 이어가며 전체1~4/1~6 완료 기준을 낮추지 않는다.
