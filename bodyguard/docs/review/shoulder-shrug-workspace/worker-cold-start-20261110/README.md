# 실제 SDK 첫 프레임 지연 재현

2026-11-10, 단일 노트북·Chrome·공개 사전 녹화 스쿼트 영상을 가상 카메라로 사용했다. 제품의 GPU 우선 `workerNativeEngine.ts`와 실제 세 모델을 사용했으며, 실제 사람의 현재 웹캠이나 동작 정답·정확도를 검증하지 않았다. 영상·관절 좌표는 저장하거나 전송하지 않았다.

## 재현과 분리

계측을 적용하지 않은 [기준 실행](baseline.json)은 첫 결과가 기한 안에 오지 않았고 종료 확인도 실패했다. 별도로 고정 단계 로그만 추가한 [GPU 계측 실행](gpu.json)은 세 모델 모두 GPU로 생성됐다. 그 첫 프레임에서 신체 추론 474.8ms, 얼굴 2,795.2ms, 손 2,217.6ms가 직렬로 이어져 약 5.49초가 걸렸다. 응답 제한을 넘겨 유효 결과는 0프레임이었으나 그 실행의 세 모델 해제 확인은 정상적으로 돌아왔다. 이는 그 실행의 현상이지, 첫 기준 실행이 같은 원인이었다는 증거는 아니다.

동일 영상의 다른 실행에서 손 CPU 우선([a](handcpu-a.json), [b](handcpu-b.json), [c](handcpu-c.json))과 세 모델 CPU 우선([a](allcpu-a.json), [b](allcpu-b.json), [c](allcpu-c.json))은 각 8프레임을 처리하고 clean 종료됐다. 각 JSON의 초기화 로그에서 실제 delegate를 확인할 수 있다. 첫 프레임에서 손 CPU 우선 조합은 신체 452~496ms·얼굴 214~223ms·손 112~129ms, 전부 CPU 우선 조합은 신체 191~210ms·얼굴 32~35ms·손 108~134ms였다.

두 runner는 실제 Worker 번들을 시험 중에만 변환해 초기화·추론·정리 단계에 고정 로그를 넣는다([GPU/손 CPU runner](gpu-handcpu-runner.mjs), [전체 CPU runner](allcpu-runner.mjs)). 원본 소스의 전후 해시는 각 결과에 일치한다. 영상의 가상 카메라 재생 시점·부하·실행 순서는 통제되지 않았고 단일 영상·단일 기기의 짧은 비교이므로 원인과 어느 delegate의 우열 또는 사람에 대한 정확도를 확정하지 않는다. 진단용 변환이 없는 기준 실행의 결과도 보존한다. CPU 우선은 수정 후보이지 종료 오류의 해결이나 출시 승인이 아니다.

샌드박스에서 로컬 포트 바인딩이 거부된 [첫 실행](sandbox.json)은 추론을 시작하지 못했다. 권한을 허용한 별도 실행이 위 기준이다. 계측 runner를 처음 복사한 뒤 원래 파일명으로 자기 해시를 읽으려다 실행 전 실패했고([오류](runner-first-failed.log.gz)), 시험 파일의 자기 참조 경로만 수정한 후 다시 실행했다. 실패를 제품 결과로 세지 않는다. 다른 앱이나 사용자의 작업은 종료하지 않았다.
