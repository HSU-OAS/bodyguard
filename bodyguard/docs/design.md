# Bodyguard — Design (기술 설계)

버전 0.3 (초안) · 2026-09-26 · 대응: `prd.md` v0.3

> 이 문서는 **어떻게 만들 것인가**를 정의한다. 무엇을 만들지는 `prd.md`에 있다.
> `[PO 제안]`은 사용자와 논의되지 않은 PO 설계이고, `[미정 Q-nn]`은 `open-questions.md`의 항목이다.
> **이 문서의 수치는 거의 전부 실측 전 초기값이다.** 확정된 값은 따로 표시한다.

## 1. 시스템 구성

```
┌──────────────────────── 브라우저 ────────────────────────┐
│                                                          │
│  웹캠 ─▶ MediaPipe Pose ─▶ 지표 계산 ─▶ 판정 ─┬─▶ 화면·아바타 │
│           (프레임 폐기)      (좌표 폐기)        ├─▶ 알림      │
│                                              ├─▶ 스트레칭   │
│                                              └─▶ 1분 집계   │
│                                                    │     │
└────────────────────────────────────────────────────┼─────┘
                                                     │ HTTPS
                                          1분 요약·기록만
                                                     ▼
                                   ┌──────────────────────┐
                                   │  FastAPI              │
                                   │  적재·조회·변화 탐지·PDF │
                                   └──────────┬───────────┘
                                              ▼
                                   ┌──────────────────────┐
                                   │  PostgreSQL 18         │
                                   └──────────────────────┘
```

**판정은 전부 브라우저에서 끝난다.** 서버는 판정하지 않는다. 쌓인 요약을 모으고, 변화를 찾고, PDF를 만든다.
영상과 관절 좌표는 브라우저 상자 밖으로 나가지 않는다 (ADR-0002, ADR-0003).
리포트 요약을 만들 때만 서버가 외부 LLM API에 집계 숫자를 보낸다 (ADR-0013).

→ ADR-0015 (2026-09-26 확정). 실제로 설치·빌드·테스트해서 고른 버전이다. 올릴 때 주의할 점도 거기 있다.

| 영역 | 선택 | 상태 |
|---|---|---|
| 런타임·패키지 | Node 24 LTS, pnpm 12 | 확정 |
| 프런트엔드 | React 19.3 + TypeScript 6.0 + Vite 8 | 확정 (React는 원문 15) |
| 라우팅 / 서버 데이터 | React Router 8 / TanStack Query 5 | 확정 |
| 스타일 | Tailwind CSS 4 | 확정 |
| 3D | Three.js 0.186 + React Three Fiber 9 + drei 10 | 확정 |

| 손가락·제스처 | MediaPipe Gesture Recognizer (Tasks Vision 1.0, 8.0MB) | 확정 (원문 54). 데모에서 동작 확인 |

| 백엔드 | Python 3.14 + FastAPI + Uvicorn + Pydantic 2, uv | 확정 |
| DB | PostgreSQL 18 + SQLAlchemy 2.1 + Alembic + psycopg 3 | 확정 |
| 인증 | Authlib(구글) + pwdlib(argon2) + aiosmtplib(팀 Gmail) + slowapi(요청 제한) | 확정 (원문 33, 42) |
| PDF | Jinja2 + WeasyPrint 70 + 나눔 폰트 | 확정. 한글 내장 확인 |
| 변화 탐지 | numpy·pandas 단순 통계 먼저, PyOD 3.6 비교 | PyOD는 검증 대상 |

| 테스트 | Vitest 5 + happy-dom + Testing Library, Playwright, pytest 9 | 확정 |

검토 후 제외한 포즈 추정 후보와 사유는 ADR-0007에 있다.

## 3. 저장소 구조

개발 폴더는 레포 안의 `bodyguard/`다(원문 38). 바깥 `docs/`는 과목 제출물이라 여기서 건드리지 않는다.

```
bodyguard/                      ← 레포 (HSU-OAS/bodyguard)
├── docs/                       과목 제출물 (사람이 관리)
└── bodyguard/                  ← 개발 폴더
    ├── AGENTS.md
    ├── README.md
    ├── docs/                   개발 문서 (이 파일)
    ├── compose.yaml            Docker Compose — PostgreSQL 18, 백엔드 (tasks #1)
    ├── frontend/               tasks #1에서 만든다
    │   └── src/
    │       ├── posture/        지표 계산·판정 — 순수 TS
    │       ├── stretch/        스트레칭 정의·판정 — 순수 TS
    │       ├── pose/           카메라, MediaPipe, 측정 루프
    │       ├── avatar/         Three.js — 내 스켈레톤, 정자세 마네킹
    │       ├── alerts/         알림 스케줄러
    │       ├── summary/        1분 집계, 업로드 큐
    │       ├── api/            백엔드 클라이언트
    │       └── pages/          화면
    └── backend/                tasks #1에서 만든다
        └── app/
            ├── api/            라우터
            ├── auth/           가입·로그인·메일 인증·구글 OAuth
            ├── models/         DB 모델
            ├── services/
            │   ├── changes/    변화 탐지
            │   ├── report/     PDF
            │   └── summary/    LLM 요약·검사
            └── tests/
```

**`posture/`와 `stretch/`는 브라우저 API를 import하지 않는다.** DOM, MediaPipe, Three.js 모두 안 된다.
관절 좌표 배열을 받아 숫자와 상태를 돌려주는 함수만 둔다. 그래야 카메라 없이 Vitest로 판정을 검증할 수 있다 (ADR-0012).

## 4. 측정 파이프라인

### 4.1 흐름
```
카메라 (getUserMedia, 640×480)
 → <video>  (제품 화면에는 보여주지 않음. 개발 빌드 디버그 화면에서만 보인다)
 → PoseLandmarker  VIDEO 모드, GPU, numPoses = 2
 → 프레임 참조 해제
 → 관절 33점 (화면 좌표 + 월드 좌표 + 가시성)
 → posture/metrics   지표 3종 계산  ── 좌표는 여기서 버린다
 → posture/state     평활 + 상태 머신
 → 화면 · 아바타 · 알림 · 1분 집계
      (스트레칭 코칭 중에는 stretch/가 좌표를 받아 판정한 뒤 버린다)
```

- 해상도 640×480, `numPoses = 2`(두 명 감지용)는 `[PO 제안]`이다
- 모델 크기는 lite(5.5MB)·full(9.0MB)·heavy(29.2MB) 중에서 M-2·M-4 실측으로 고른다. 데모에서 셋을 바꿔 가며 비교한다(원문 52). 원문 6("작은 모델")과 P8(가볍게)에 따라 정확도가 충분한 가장 작은 모델을 제품 기본값으로 한다
- 모델 파일(`.task`)은 레포에 넣지 않는다(`.gitignore`). 빌드 때 내려받아 우리 정적 호스팅에서 제공한다
- MediaPipe WASM(변형마다 약 11~12MB)은 Vite가 챙겨 주지 않는다. `node_modules/@mediapipe/tasks-vision/wasm`을 정적 폴더로 복사하는 스크립트를 둔다. 브라우저는 그중 하나만 받는다

### 4.2 화면이 보일 때
`requestVideoFrameCallback`으로 프레임마다 깨어나되, 추론은 **초당 30회로 제한**한다. 처음엔 15회였는데 부족하다는 의견에 30으로 올렸다(원문 50).
- 카메라 프레임 간격이 흔들려도 평균이 제한값에 맞도록, 지난 시간만큼 예산을 쌓아 두고 1회분이 차면 추론한다
- 대가는 계산량이다. 첫 실측(1회 18.2ms) 기준으로 30회면 메인 스레드 시간의 절반 이상을 쓴다. 화면이 버벅이면 추론을 워커로 옮긴다(§4.3 방식 b). 부담은 M-5에서 잰다

### 4.3 탭이 가려졌을 때 — M-1
탭이 가려지면 크롬은 `requestAnimationFrame`과 `requestVideoFrameCallback`을 멈추고 타이머를 늦춘다.
5분 넘게 가려진 탭은 타이머가 1분 단위로 묶일 수도 있다. **카메라를 쓰는 탭이 예외인지는 직접 재야 한다.**

아래 순서로 시험하고, 되는 첫 방식을 쓴다.

| 순서 | 방식 | 걱정되는 점 |
|---|---|---|
| a | 메인 스레드 1초 타이머 + 같은 `<video>`에서 추론 | 가려진 탭의 타이머 제한, 가려진 video의 프레임 갱신 여부 |
| b | Worker의 1초 타이머 + `MediaStreamTrackProcessor`로 프레임을 받아 Worker 안에서 추론 | 크롬·엣지 전용 API. Worker 안 MediaPipe GPU 동작 확인 필요 |
| c | 가려진 동안 측정 중지 (폴백) | 작업 중 자세 알림이 사라진다 |

시험 조건: 크롬·엣지 각각, 5분·30분 방치, 전원 연결·배터리. 측정 간격을 로그로 남긴다.
결과는 ADR-0004에 적는다.

### 4.4 시간은 샘플 수가 아니라 실제 시간으로 센다
보일 때는 초당 15회, 가려지면 초당 1회로 샘플 간격이 달라진다. 알림 타이머와 1분 집계는 **샘플 사이의 실제 경과 시간**으로 센다.
타이머가 늦게 깨어나도 시간 계산은 틀리지 않는다.

## 5. 자세 지표 정의 `[PO 제안]` `[미정 Q-05]`

### 5.1 문제
차터의 지표 이름 중 "목 전방 경사각"과 "상체 전방 굴곡각"은 **옆에서 본 각도**다.
노트북 웹캠은 정면에서 찍는다. 정면 영상에서 앞뒤 움직임은 깊이(z) 추정값이나 크기 변화로만 드러난다.
그래서 두 지표는 후보를 2개씩 두고 실측(M-3, M-4)으로 고른다.

### 5.2 기호
MediaPipe 관절 번호: 0 코, 7·8 귀, 11·12 어깨, 13·14 팔꿈치, 15·16 손목, 23·24 엉덩이

| 기호 | 뜻 |
|---|---|
| `S`, `E`, `H` | 어깨·귀·엉덩이 좌우 중점 (화면 좌표, 가로세로 비율 보정) |
| `Sw`, `Ew`, `Hw` | 같은 점의 월드 좌표 (미터, 엉덩이 중심 원점) |
| `w` | 어깨 너비 `|P11 − P12|` (화면 좌표) |
| `base` 첨자 | 기준선 보정 때의 값 |

월드 좌표 축의 부호는 구현할 때 확인한다.

### 5.3 어깨 좌우 기울기 — 정면에서 바로 잰다
```
θs = 어깨선(P11→P12)이 수평과 이루는 각도 (°)
편차 = θs − θs_base
```
필요 관절: 11, 12. 정면 카메라에서 가장 믿을 만한 지표다. 기준선 없이도 수평(0°)을 기준으로 쓸 수 있다.

### 5.4 목 전방 — 후보 2개, M-4로 고른다
| 후보 | 계산 | 표시 |
|---|---|---|
| A. 깊이 각도 | `Sw→Ew` 벡터를 옆면(y–z 평면)에 투영해 수직과 이루는 각도 `θn`. 편차 = `θn − θn_base` | ° |
| B. 2D 지수 | `rn = (S.y − E.y) / w` — 귀가 어깨선 위로 떨어진 거리를 어깨 너비로 나눈 값. 머리를 내밀고 숙이면 작아진다. 편차 = `(rn_base − rn) / rn_base` | % |
| C. 얼굴·어깨 크기 비율 | `k = (f / f_base) / (w / w_base)` — `f`는 얼굴 크기(MediaPipe Face Landmarker). 머리만 앞으로 나오면 얼굴만 커져서 `k`가 1보다 커진다. 몸 전체가 다가오면 둘 다 커져 `k`는 그대로다. 고개 숙인 각도(pitch)도 같이 나온다 | % |
| D. 단안 깊이 모델 | 깊이 모델(Depth Anything V2 Small 등)로 깊이 지도를 만들고 얼굴과 어깨 위치의 깊이 차이를 본다. 1초에 한 번만 돌린다 | cm 또는 % |

A가 흔들리지 않으면 A를 쓰고 차터 이름대로 "각"으로 부른다. 아니면 B·C·D 중 정답(§5.7)과 가장 잘 맞는 것을 쓰고 이름을 "목 전방 지수"로 바꾼다.
귀가 머리카락·헤드폰에 가릴 때 코(0)로 대신할지도 M-4에서 본다.

D에 대한 솔직한 전망(원문 40):
- 깊이 모델은 방 전체의 멀고 가까움에는 강하지만, 몸 위 몇 cm 차이를 정확히 잡는다는 보장이 없다
- 상대 깊이만 주는 모델은 프레임마다 기준이 달라져 값이 출렁인다. 기준점으로 나눠 정규화해야 한다
- MediaPipe 옆에서 모델을 하나 더 돌리므로 무겁다(M-5). 모델 파일도 수십 MB다
- 라이선스가 모델 크기마다 다르다. Depth Anything V2는 Small만 Apache-2.0이고 큰 모델은 비상업용이다
- MediaPipe가 이미 관절마다 깊이(z)를 주므로 A로 충분하면 D는 필요 없다

### 5.5 상체 전방 굴곡 — 후보 2개, M-3로 고른다
| 후보 | 계산 | 조건 |
|---|---|---|
| A. 깊이 각도 | `Hw→Sw` 벡터를 옆면에 투영해 수직과 이루는 각도 `θt` | 엉덩이 가시성 0.5 이상 |
| B. 대리 지표 | `g = w / w_base` (몸이 카메라 쪽으로 오면 커짐), `v = (S.y − S.y_base) / w_base` (어깨가 내려온 정도) | 엉덩이가 안 보일 때 |

솔직한 한계:
- 노트북 웹캠에서는 책상 때문에 엉덩이가 거의 안 보인다. 안 보여도 MediaPipe는 엉덩이 좌표를 **지어내서** 준다. 가시성 값으로 걸러야 한다
- B는 "허리를 편 채 화면 쪽으로 다가앉음"과 "구부정하게 숙임"을 구분하지 못한다
- 둘 다 불안정하면 이 지표를 빼고 2개로 간다 (원문 10은 "2, 3개")

### 5.6 카메라 위치
노트북 웹캠은 보통 아래에서 위로 찍는다. 기준선 대비 편차를 쓰므로 고정된 기울기는 상쇄된다.
**측정 중에 노트북 화면 각도를 바꾸면 기준선이 틀어진다.** 전체 관절이 한꺼번에 크게 이동하면 재보정을 권한다 `[PO 제안]`.

### 5.7 지표를 고르는 방법 — 옆모습 정답지 `[PO 제안]`
정면 지표가 맞는지 보려면 "정답"이 있어야 한다. 옆모습에서는 목과 상체의 앞뒤 각도를 직접 잴 수 있다.

- 노트북 웹캠(정면)과 옆에 세운 폰 카메라(옆모습)로 동시에 잰다. 둘 다 MediaPipe를 돌려 **관절 좌표만** 저장한다. 영상은 저장하지 않는다
- 두 기기의 시각을 맞추려고 시작할 때 손을 드는 동작을 넣는다
- 옆모습에서 구한 목·상체 각도를 정답으로 삼는다. 연구에서 쓰는 두개척추각(CVA) 같은 지표라 참고 자료를 찾을 수 있다
- 자세 목록: 정자세, 목 내밀기, 폰 보듯 고개 숙이기, 어깨 한쪽 내리기, 구부정하게 숙이기, 허리 편 채 다가앉기, 뒤로 기대기, 턱 괴기. 강도 3단계, 두 명
- 기록하는 동안 키보드로 자세 번호를 눌러 라벨을 남긴다

후보마다 네 가지를 본다.
1. 옆모습 정답과 같이 움직이는가
2. 정자세와 나쁜 자세를 가르는가
3. 가만히 있을 때 얼마나 흔들리는가
4. CPU를 얼마나 쓰는가

임계값(§6.1)은 정자세와 나쁜 자세의 값 분포를 가장 잘 가르는 지점으로 정한다.
**임계값을 맞출 때 쓴 데이터로 일치율(NFR-04)을 재지 않는다.** 다른 날·다른 사람 데이터로 따로 잰다. 안 그러면 숫자가 부풀어 보인다.

## 6. 판정 `[PO 제안]` `[미정 Q-06]`

### 6.1 임계값 초기값
근거 없는 초기값이다. 옆모습 정답지 실험(§5.7)으로 다시 정한다.
민감도는 사용자에게 주지 않는다. 팀이 정한 값을 모두에게 쓴다(원문 44).

| 지표 | 주의 | 이탈 |
|---|---|---|
| 어깨 좌우 기울기 | 편차 2.5° 이상 | 편차 5° 이상 |
| 목 전방 (A 각도) | 5° 이상 | 10° 이상 |
| 목 전방 (B 지수) | 7.5% 이상 | 15% 이상 |
| 상체 굴곡 (A 각도) | 7.5° 이상 | 15° 이상 |
| 상체 굴곡 (B 대리) | `g` 1.05 이상 | `g` 1.10 이상 |

### 6.2 상태 머신
```
                 편차 ≥ 이탈 임계, 3초 지속
   좋음 / 주의 ──────────────────────────▶ 이탈
        ▲                                   │
        └──── 편차 < 이탈 임계 × 0.8, 2초 ────┘

   어느 상태든: 가시성 < 0.5 또는 2명 이상 → 측정 불가
```

| 상수 | 값 | 이유 |
|---|---|---|
| 평활 시간 상수 | 0.5초 | 손떨림·검출 흔들림 제거. 화면 1초 반응(NFR-02) 안에 들어온다 |
| 이탈 진입 | 3초 지속 | 고개를 잠깐 숙인 것을 이탈로 세지 않는다 |
| 이탈 해제 | 임계의 80% 안, 2초 | 경계에서 깜빡이지 않게 |
| 가시성 기준 | 0.5 | MediaPipe가 지어낸 좌표 거르기 |
| 화면 밖 관절 | 가시성과 상관없이 쓰지 않음 | 화면 밖 관절도 가시성이 높게 나올 때가 있다 (데모에서 확인) |
| 미검출 일시정지 | 5초 | FR-M-07 |

좋음·주의는 순간값으로 바로 바뀐다(화면용). 이탈은 지속 시간을 본다(알림·기록용).
**모든 상수는 `frontend/src/posture/thresholds.ts` 한곳에 둔다.** 실측하면서 계속 바뀐다.

### 6.3 색
→ 원문 43, ADR-0014

| 상태 | 색 |
|---|---|
| 좋음 | 초록 |
| 주의 | 주황 |
| 이탈 | 빨강 |
| 측정 불가 | 회색 |
| 지표와 상관없는 부위 | 중립색 |

- 색은 내 몸을 따라 움직이는 스켈레톤에 칠한다 (§9.1)
- 편차가 이탈 임계를 넘어도 3초가 지나기 전에는 주황으로 보인다. 3초가 지나면 빨강이 된다
- 색 값도 상수로 한곳에 둔다
- 색을 구분하기 어려운 사용자를 위해 상태 글자를 같이 띄운다 `[PO 제안]`

## 7. 알림 스케줄러

→ FR-N-01 ~ FR-N-05, ADR-0010. 세부는 `[PO 제안]` Q-07, Q-08

### 7.1 자세 이탈 타이머
```
매 샘플마다 (실제 경과 시간 dt)
  이탈        → 이탈 누적 += dt, 복귀 누적 = 0
  좋음/주의   → 복귀 누적 += dt; 복귀 누적 ≥ 30초면 이탈 누적 = 0
  측정 불가   → 둘 다 그대로 (멈춤)
  이탈 누적 ≥ 설정값(5분) 이고 마지막 알림 후 10분 지남 → 알림, 이탈 누적 = 0
```

### 7.2 오래 앉음 타이머
```
  사람이 보임  → 앉은 시간 += dt, 안 보인 시간 = 0
  사람이 안 보임 → 안 보인 시간 += dt; 3분 넘으면 앉은 시간 = 0
  스트레칭 완료 → 앉은 시간 = 0
  앉은 시간 ≥ 설정값(50분) → 알림, 앉은 시간 = 0
```

### 7.3 M-1이 실패했을 때
탭이 가려진 동안 측정하지 못하면:
- 자세 이탈 타이머는 멈춘다
- 앉은 시간은 **계속 센다.** 다른 창에서 일하고 있을 가능성이 높다고 본다

### 7.4 알림 띄우기
- `Notification` API. `tag`를 알림 종류별로 고정해 쌓이지 않게 한다
- 알림을 누르면 Bodyguard 탭으로 돌아와 스트레칭 화면을 연다
- 권한이 없으면 화면 안 알림만 띄운다
- 알림을 띄운 시각과 사용자의 반응(스트레칭 함 / 닫음 / 반응 없음)을 기록한다

## 8. 스트레칭 판정

### 8.1 정의 형식
동작은 코드가 아니라 데이터로 정의한다. 8종 목록은 `prd.md` FR-S-01 `[PO 제안]` Q-09.

```ts
type StretchDef = {
  id: string                       // 'neck_side_tilt'
  name: string                     // '목 옆으로 기울이기'
  part: 'neck' | 'shoulder' | 'back' | 'waist'
  kind: 'hold' | 'reps'
  sides: 'both' | 'none'
  holdSec?: number                 // 유지형
  reps?: number                    // 반복형
  repHoldSec?: number
  requiredLandmarks: number[]
  check: (pose: Pose, base: Baseline, side?: Side) => { ok: boolean; failing: BodyPart[] }
}
```

`check`는 순수 함수다. 동작별 픽스처(팀원이 직접 한 동작의 랜드마크 기록)로 Vitest에서 검증한다.

### 8.2 진행
- 유지형: `ok`인 동안 타이머가 돈다. 1초 넘게 깨지면 멈추고, 다시 `ok`면 이어서 센다
- 반복형: `대기 → 조건 충족(repHoldSec 유지) → 원위치 복귀 → 1회` 상태 머신
- `failing`에 담긴 부위를 아바타에서 빨갛게 칠한다
- 판정이 끝나면 좌표는 버리고 결과(동작, 방향, 통과·건너뜀·중단, 걸린 시간, 시작 경로)만 남긴다

## 9. 스켈레톤과 마네킹

→ FR-A-01 ~ FR-A-03, ADR-0009, ADR-0014

화면에는 두 가지가 뜬다.

| | 내 스켈레톤 | 정자세 마네킹 |
|---|---|---|
| 움직임 | 내 몸을 따라 움직인다 | 정자세로 고정 |
| 판정 색 | 여기에 칠한다 (확정, 원문 43) | 칠하지 않는다 `[PO 제안]` Q-10 |
| 모습 | 점과 선, 머리는 둥근 얼굴 (원문 55) | 뼈대로 시작해 마네킹으로 (ADR-0009) |
| 역할 | 지금 어디가 틀어졌는지 | 어떤 자세가 맞는지 |

웹캠에 보이는 범위와 맞춰 둘 다 상반신만 보여준다 `[PO 제안]`.

### 9.1 내 스켈레톤
- MediaPipe 월드 좌표로 Three.js 장면에 점과 선을 그린다. 좌표는 그리는 데만 쓰고 버린다
- 선을 부위로 묶어 부위마다 판정 색(§6.3)을 준다

| 부위 | 이루는 선 | 연결 지표 |
|---|---|---|
| 머리·목 | 둥근 머리, 귀 중점 → 어깨 중점 | 목 전방 |
| 어깨 | 11 ↔ 12 | 어깨 좌우 기울기 |
| 몸통 | 어깨 → 엉덩이 | 상체 전방 굴곡 |
| 팔 | 어깨 → 팔꿈치 → 손목 | 없음 (중립색) |

- 가시성이 낮은 관절과 그 관절에 닿는 선은 흐리게 그리거나 숨긴다. 책상에 가린 엉덩이를 지어낸 위치에 그리지 않는다
- 스트레칭 중에는 통과 조건을 못 채운 부위를 빨갛게 칠한다 (FR-S-03)

**둥근 머리** (원문 55·57, ADR-0017, `frontend/src/avatar/face.ts`, `faceTracking.ts`)
- 얼굴 관절(0~10번)은 선이나 점으로 그리지 않는다. 대신 둥근 머리에 점 눈(하이라이트), 볼터치, 웃는 입을 그린다
- 자리와 크기는 몸 모델로 정한다. 코와 양 귀(0, 7, 8) 중 하나라도 믿을 수 없으면 머리를 그리지 않는다
- 반지름은 귀 사이 거리의 0.95배로 실제 머리보다 크게, 중심은 귀 높이에서 머리 위쪽으로 반지름의 0.25배 올린다. 2등신 캐릭터처럼 보이고 턱이 어깨에 닿지 않는다
- 방향은 얼굴 모델(Face Landmarker)의 얼굴 변환 행렬로 정한다. 측정 시작 뒤 얼굴이 처음 보인 2초의 평균 방향을 정면으로 삼고, 거기서 돌린 만큼만 돌린다. 이 기준은 그리는 데만 쓰고 판정에는 쓰지 않는다
- 떨림: 머리 방향을 0.05초 시간 상수로 부드럽게 한다. 3D는 추론 사이 화면 프레임도 약 0.05초로 이어 준다
- 눈·입: 얼굴 478점에서 눈꺼풀 사이 ÷ 눈 너비, 입술 사이 ÷ 입 너비를 잰다. 눈은 정면 기준 2초의 값(중앙값)을 평소로 보고, 덜 뜨면 세로로 납작해져 감으면 선만 남는다. 입을 벌리면 웃는 입 대신 벌린 입을 그린다. 표정 계수(blendshapes)는 쓰지 않는다
- 얼굴 모델을 끄거나 얼굴을 못 찾으면 정면을 본다
- 2D는 원본 영상 좌표로 그리고 CSS로 뒤집는다. 3D는 장면을 뒤집어 그리므로 방향과 눈 좌우도 뒤집는다 (`turnAxes`, `eyeOpen`)
- 고개를 돌리면 뒤로 넘어간 눈·볼은 그리지 않는다. 얼굴 재질은 톤 매핑을 꺼서 2D와 같은 색으로 보인다
- 판정 색을 머리에 어떻게 입힐지는 `[미정 Q-30]`. 아바타가 생기면(§9.6) 이 머리는 아바타로 바뀐다
- 지난 방식의 문제 (2026-09-27 녹화 분석, 원문 56): 몸 모델 얼굴 점의 깊이값 z로 방향을 구했더니 늘 아래를 보고(2D 중앙값 41°, 3D 32°) 2D는 0.1초 사이 좌우로 최대 20°씩 튀었다. 그래서 얼굴 모델로 바꿨다

### 9.2 정자세 마네킹
1. **뼈대** — 정자세 관절 위치를 점과 선으로 그린다. 에셋 없이 바로 만든다
2. **마네킹** — 같은 자리에 얼굴 없는 단색 인체 모델을 놓는다

리타게팅은 하지 않는다(FR-A-03). 스트레칭 때는 동작별 목표 자세를 보여준다.

### 9.3 모델 에셋 조건 `[미정 Q-11]`
- glTF(GLB), 사람형 뼈대(척추·목·머리·어깨·팔), 5MB 이하
- 라이선스 CC0 또는 CC-BY. 재배포를 막는 무료 에셋은 쓰지 않는다
- 스트레칭 시범은 동작별 시작·목표 자세를 뼈 회전값 키프레임으로 직접 만든다 `[PO 제안]`

### 9.4 가볍게
- 스켈레톤은 추론과 같은 속도(최대 30fps)로 그린다. 마네킹은 자세가 바뀔 때만 다시 그린다
- 탭이 가려지면 그리지 않는다
- 마네킹 로드에 실패하면 정자세 뼈대로 돌아간다 (FR-A-02)


### 9.5 손가락 (원문 53·54, ADR-0016)
- MediaPipe Gesture Recognizer로 손마다 21점과 제스처를 받는다. 두 손까지
- 2D는 몸과 같은 화면 좌표라 그대로 그린다
- 3D는 손 모델의 월드 좌표가 손 중심 기준이라, 손의 손목을 몸 모델의 손목 위치로 옮겨 붙인다. 두 좌표계의 축이 같다고 보고 위치만 맞추므로 크기·방향은 근사치다
- 어느 손인지는 몸 손목과 가까운 쪽으로 정한다. MediaPipe의 왼손·오른손 표시는 거울 화면을 가정해서 쓰지 않는다
- 손가락이 붙은 쪽은 몸 모델의 거친 손 점(엄지·검지·새끼 뿌리)을 그리지 않는다
- 계산: 몸 추론에 손 추론이 더해진다. 합이 33ms를 넘으면 30fps를 못 채운다. 그때는 손을 두 프레임에 한 번 돌리거나 몸 모델을 낮춘다

### 9.6 내 동작을 따라 움직이는 아바타 (추후, `[미정 Q-28]`)
- 추후에는 스켈레톤 대신 사용자가 고르거나 내 체형에 맞춘 아바타가 내 동작을 따라 움직인다 (원문 54)
- 필요한 것: 손가락 뼈까지 있는 사람형 뼈대(리그)의 아바타 에셋, 관절 좌표를 뼈 회전값으로 바꾸는 리타게팅, 체형 맞춤
- 리타게팅은 직접 만들지(관절 방향으로 뼈 회전 계산) 공개 라이브러리를 쓸지 그때 조사해 정한다. 유지보수 상태를 꼭 본다
- 체형 맞춤 `[PO 제안]`: 보정 때 잰 관절 비율(어깨 너비, 팔 길이)로 아바타 뼈 길이를 맞춘다

## 10. 1분 요약과 업로드

→ FR-R-01, FR-R-02, ADR-0003

- 시계 기준 1분(00초~59초) 단위로 묶는다. 저장은 UTC, 날짜 구분은 한국 시간 `[PO 제안]` Q-18
- 샘플 간격이 다르므로 실제 경과 시간으로 가중한다 (§4.4)
- 브라우저의 IndexedDB 큐에 넣고, 5분마다 · 탭이 가려질 때 · 페이지를 닫을 때(`fetch` keepalive) 묶어서 올린다 `[PO 제안]`
- 서버는 `(user_id, minute_start)`로 덮어쓴다. 같은 분이 두 번 와도 하나만 남는다
- 로그인하지 않았으면 요약을 만들지 않는다 `[PO 제안]` Q-15

요청 예시:
```json
POST /api/v1/summaries/batch
{
  "items": [
    {
      "minute_start": "2026-10-06T01:23:00Z",
      "baseline_id": "b-uuid",
      "measured_sec": 58,
      "unmeasurable_sec": 2,
      "present_sec": 60,
      "background_sec": 0,
      "neck":     { "dev_mean": 6.2, "bad_sec": 12 },
      "shoulder": { "dev_mean": 1.1, "bad_sec": 0 },
      "trunk":    { "dev_mean": null, "bad_sec": 0 },
      "any_bad_sec": 12
    }
  ]
}
```

`trunk`가 `null`이면 그 1분 동안 상체 지표를 잴 수 없었다는 뜻이다.

## 13. 인증

→ FR-U-01 ~ FR-U-05, ADR-0006. FastAPI에서 직접 만든다(원문 42).

### 13.1 엔드포인트 `[PO 제안]`
| 메서드 | 경로 | 용도 |
|---|---|---|
| POST | `/auth/signup` | 이메일·비밀번호를 받고 인증 코드 메일 발송 |
| POST | `/auth/verify` | 코드 대조 → 가입 완료 |
| POST | `/auth/resend` | 인증 코드 재발송 (60초 간격) |
| POST | `/auth/login` | 이메일 로그인 |
| GET | `/auth/google/login`, `/auth/google/callback` | 구글 OAuth |
| POST | `/auth/password/forgot` | 재설정 메일 발송 (가입 여부와 상관없이 같은 응답) |
| POST | `/auth/password/reset` | 새 비밀번호 설정, 기존 로그인 전부 끊기 |
| POST | `/auth/logout` | 로그아웃 |

### 13.2 메일 — 팀 Gmail
- 팀 공용 Gmail 계정을 만들고 2단계 인증을 켠 뒤 **앱 비밀번호**로 SMTP 발송한다
- 앱 비밀번호는 서버 `.env`에만 둔다. 레포의 `.env.example`에는 변수 이름만 적는다
- 메일은 양식(HTML 템플릿)에 코드나 링크를 채워 보낸다
- 발송은 요청 처리와 분리한다(백그라운드 작업). 실패하면 재발송을 안내한다
- 개인 Gmail은 하루 발송량이 약 500통으로 제한된다. 사용자 테스트 규모에는 충분하다
- 학교 메일(hansung.ac.kr)로 보냈을 때 스팸함으로 가는지 먼저 확인한다
- 이 계정의 2단계 인증을 누구 폰에 걸지, 비밀번호를 누가 관리할지 정해 둔다

### 13.3 코드·토큰
| 항목 | 값 `[PO 제안]` |
|---|---|
| 가입 인증 코드 | 6자리 숫자, 10분 만료, 5회 틀리면 무효 |
| 재발송 간격 | 60초 |
| 비밀번호 재설정 | 링크 토큰 30분, 한 번만 사용 |
| 저장 | 코드·토큰 모두 해시로만 저장 |
| 비밀번호 | argon2id 해시 |

### 13.4 요청 횟수 제한
가입·재발송·재설정 요청을 같은 IP와 같은 이메일 기준으로 제한한다.
안 하면 누군가 우리 가입창으로 남의 주소에 메일을 계속 보낼 수 있고, 그러다 팀 Gmail 계정이 정지될 수 있다.

### 13.5 구글 로그인
- Google Cloud에서 OAuth 클라이언트를 만든다. 요청 범위는 이메일·프로필만
- 동의 화면이 '테스트' 상태면 등록한 테스트 사용자(최대 100명)만 로그인할 수 있다. 사용자 테스트 전에 게시 상태를 확인한다
- 이미 이메일로 가입한 주소로 구글 로그인을 하면 계정을 합치지 않고 안내만 한다 `[PO 제안]`

### 13.6 로그인 유지 `[PO 제안]`
- 로그인하면 서버가 세션 토큰을 httpOnly 쿠키로 준다. 브라우저 스크립트가 토큰을 읽지 못한다
- 쿠키를 쓰므로 상태를 바꾸는 요청에는 CSRF 방어를 건다

## 14. 변화 탐지 `[PO 제안]` `[미정 Q-12]`

→ FR-R-04

| 항목 | 제안 |
|---|---|
| 일별 값 | 지표별 이탈 비율(이탈 시간 / 측정 시간), 지표별 평균 편차 |
| 유효한 날 | 측정 60분 이상 |
| 시작 조건 | 유효한 날 7일 이상 |
| 비교 창 | 오늘을 뺀 직전 14 유효일 |
| 1차 방법 | 로버스트 z = (값 − 중앙값) / (1.4826 × MAD). 절댓값 3 이상이면 표시 |
| 2차 방법 | 같은 입력으로 PyOD(ECOD 등)를 돌려 비교. 1차보다 나을 때만 채택 |
| 재보정 | 평균 편차는 기준선이 바뀌면 끊는다. 이탈 비율은 "내 기준선에서 벗어난 시간"이라 이어서 본다 |
| 계산 시점 | 대시보드 요청 때 계산하고 캐시한다. 데이터가 작다 |
| 표시 | 대시보드 배너와 리포트. 푸시 알림은 없다 |

솔직한 전망: 입력이 하루 한 점이고 2주치면 14점이다. 이 크기에서 이상 탐지 모델이 중앙값·MAD보다 나을 이유가 뚜렷하지 않다.
PyOD는 차터에 적힌 검증 대상이라 비교는 하되, 결과로 판단한다.

## 15. 리포트 PDF와 LLM 요약

→ FR-R-05

- 서버에서 만든다. 요청 때 생성하고 저장하지 않는다
- 흐름: 기간 조회 → HTML 템플릿에 채움 → PDF 변환
- WeasyPrint(HTML→PDF, BSD-3-Clause)로 만든다 (ADR-0015). 한글은 나눔 폰트(OFL)를 이미지에 넣는다. 나눔고딕 내장과 한글 텍스트 추출까지 확인했다
- 차트는 서버에서 SVG로 그린다
- 1~2쪽. 첫 장에 고지 문구(FR-R-05)
- 담을 내용은 `[미정 Q-13]`

### 15.1 LLM 요약 (FR-R-07, ADR-0013)
```
리포트 요청
 → 기간 집계 (숫자만: 측정 시간, 지표별 이탈 비율·평균 편차, 스트레칭 수행·건너뜀, 알림 수, 변화 표시일)
 → 저장된 요약이 있으면 그대로 쓴다
 → LLM API 호출 (서버에서만, 10초 제한)
 → 검사
     ├ 문장 속 숫자가 전부 입력에 있는가
     ├ 질환명·진단·치료·권유 표현이 없는가 (금지어 목록)
     └ 한 단락 길이 안인가
 → 통과: 리포트 첫 장에 넣고 report_summaries에 저장
 → 실패: 요약 없이 리포트
```
- 입력에 이름·이메일·계정 ID를 넣지 않는다
- 지시문은 "주어진 숫자만 설명한다. 원인·질환·권유를 말하지 않는다"로 고정한다
- 모델 고르기: 회사별 가장 싼 모델 2~3개에 같은 테스트 입력 20개를 넣어 검사 통과율을 본다. 통과하는 것 중 가장 싼 걸 쓴다(원문 41). 이 결과가 과목의 Hallucination 평가 자료가 된다
- 비용: 한 장에 입력 3천·출력 5백 토큰 정도다. Claude에서 가장 싼 Haiku 4.5(100만 토큰당 입력 $1·출력 $5)면 장당 약 8원이다(2026-09 요금, 환율 1,400원)
- 사용자당 하루 생성 횟수를 제한한다 `[PO 제안]` Q-27
- API 키는 서버 `.env`에만 둔다

## 17. 배포 `[미정 Q-04]`

- 개발: localhost. HTTPS 없이도 카메라가 켜진다
- 배포: 프런트는 정적 빌드(node:24에서 빌드), 백엔드는 python:3.14-slim에 Pango와 나눔 폰트를 넣은 이미지, DB는 postgres:18 컨테이너
- 백엔드 이미지는 검증 때 1.4GB였다. 운영 이미지에서는 개발 도구를 빼고, 단순 통계로 충분하면 PyOD를 빼서 줄인다 (ADR-0015)
- **배포 주소는 반드시 HTTPS**다. 아니면 카메라가 켜지지 않는다
- 사용자 테스트 전까지 정하면 된다

## 18. 목표와 설계의 대응

목표마다 **어느 설계가 책임지는지** 적는다. 담당 설계가 없는 목표는 달성되지 않는다.

| NFR | 목표 | 책임지는 설계 |
|---|---|---|
| NFR-01 | 15fps 이상 | §4.1 lite 모델 우선 · §4.2 GPU 추론 · FR-M-08 해상도 하향 |
| NFR-02 | 피드백 1초 이내 | §6.2 평활 0.5초 · 화면은 순간값, 판정만 지속 시간 사용 |
| NFR-03 | 뒤 탭 약 1초 간격 | §4.3 방식 a → b → c |
| NFR-04 | 일치율 80% | §5.7 옆모습 정답지로 지표 선택·임계값 조정 · 애매하면 측정 불가 |
| NFR-05 | 사용자 테스트 | tasks P7 |
| NFR-06 | CPU 부담 (목표 미정) | §4.2 30회 제한(버벅이면 워커) · §9.4 그리기 최소화 · §4.3 가려지면 1초 간격 |
| NFR-07 | 개인정보 | §1 판정은 브라우저에서 · §11 좌표 컬럼 없음 · §16 |

**NFR-02와 NFR-04가 부딪히는 지점**이 §6.2다. 평활과 지속 시간을 늘리면 오판정은 줄지만 반응이 늦어진다.
그래서 화면 반응과 판정을 나눴다. 화면은 0.5초 평활만 거쳐 바로 바뀌고, 알림과 기록에 쓰는 이탈 판정만 3초를 기다린다.
